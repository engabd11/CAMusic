## 1. What v0.5.0 Is

CAMusic (formerly Sendspin) is a native Android music player that serves two roles:

1. **A Music Assistant Sendspin player** — registers as a real player over WebSocket, receives clock-synced binary audio (FLAC/Opus/PCM), decodes locally, and plays through `AudioTrack`. Sample-accurate multi-room sync via NTP-style Kalman filter.
2. **A standalone Navidrome/OpenSubsonic client** — browses, streams, downloads, and plays offline through ExoPlayer with gapless, ReplayGain, and exact seek.

Plus: per-player parametric EQ (via MA's DSP pipeline), speaker grouping, queue management, lyrics, Light Sync (syncoV2 via HA), downloads, and a Material 3 OLED design system with album-derived accent colors.

**26,014 lines of Kotlin** across 84 source files. **167 JVM unit tests** covering protocol, clock, scheduling, parsing, DSP, lyrics, and ReplayGain. **505 lines of C/C++** (native AAudio I24 pipeline — written, not compiled, not called).

## 2. What's Working Well

### Audio Pipeline
- **Clock sync**: NTP 4-point exchange → 2-D Kalman filter (offset + drift). Convergence-gated playback start. Sync mute until converged. All JVM-tested.
- **24-bit bit-perfect** (Kotlin path): `FormatNegotiator` advertises 24-bit when bit-perfect is on. `SendspinAudioEngine` requests `ENCODING_PCM_FLOAT` from FLAC decoder, builds track from decoder-reported format (never server-claimed). 176.4/192 kHz gated behind device probe.
- **ReplayGain** (Navidrome path): Off/track/album modes, +3 dB boost cap, applied as scalar on ExoPlayer volume. Album mode default.
- **USB DAC routing**: `AudioOutputs` detects, lists, and routes to USB devices via `setPreferredDevice`. Device capabilities probed via `getMinBufferSize`.
- **Gapless** (Navidrome path): ExoPlayer owns the whole queue, buffers across boundaries.
- **Stream continuity** (MA path): Codec/AudioTrack reuse across track boundaries when format matches. Tail drains rather than discards.

### Protocol
- **Ordered inbox**: Single `Channel<Inbound>` for text + binary, one consumer. `stream/clear` can't be reordered past audio.
- **Flexible duration**: Accepts `Long` or `Double` for timestamps (MA sends floats).
- **Reconnect with backoff**: Capped at 15s, resets on successful handshake.
- **`group/update`**: Parsed and forwarded to Speakers screen for instant group state.

### Library & Control
- **MA**: Full browse (artists/albums/tracks/playlists), search, shelves (recent, recommendations, favorites, in-progress), queue management (view/jump/reorder/remove/clear/save-as-playlist/transfer), playlist CRUD, favorites, similar tracks, sonic text search, lyrics, DSP config, player config.
- **Navidrome**: Full browse (artists/albums/playlists/genres/starred), search3, lyrics (structured + legacy with mismatch check), artist/album info, playlist CRUD, star/rate, scrobble (now-playing + completed), cross-device play queue.
- **Downloads**: Track/album/playlist, original files, cover caching (per-album), Wi-Fi-only, storage cap, offline playback, progress UI.

### UI/UX
- **Material 3 Expressive**: Full M3 theme, OLED black default, album-derived accent, 4 theme options (OLED/dark/light/system), 3 accent sources (album/dynamic/fixed).
- **Motion**: Shared element transitions (album art flies to detail screen), screen push/pop, animated list items, sheet springs, predictive back.
- **Performance**: Baseline profile shipped, lazy lists with keys + contentType, 0.20% janky frames at 120Hz, flow consolidation (7 shelves → 1 flow).
- **Settings**: Categorized (Servers, Library, Audio, Downloads, Appearance, Player), each a short list.

### Security
- **Credentials**: AES-256-GCM via Android Keystore. Passwords and HA tokens encrypted at rest.
- **Token auth**: Subsonic uses `t = md5(password + salt)`, password never on URL.
- **Legacy fallback**: Plaintext values still read (re-encrypted on next write).

## 5. New Opportunities (Post-0.5.0 Roadmap)

### Tier 1 — Audiophile Differentiators

These are the features that make the app **the** player for someone who cares about sound quality.

#### 1. Native AAudio Bit-Perfect Output
**What:** Enable the C++ AAudio I24 exclusive-mode pipeline. Bypass the Android mixer entirely for true bit-perfect output.

**Why:** The current 24-bit path goes through `AudioTrack` → Android mixer → DAC. The mixer resamples to the device's native rate and applies system volume. Exclusive-mode AAudio writes directly to the DAC — no resampling, no system volume interference, no other app's audio mixed in.

**How:**
1. Uncomment `externalNativeBuild` in `build.gradle.kts`.
2. Add JNI bridge in Kotlin: `external fun engine_start(...)`, etc.
3. In `SendspinAudioEngine`, add a `NativeEngine` path: when bit-perfect is on AND the device supports exclusive mode, route to native. Fall back to `AudioTrack` when exclusive can't be opened.
4. The native engine already requests `SharingMode::Exclusive` with `Shared` fallback.
5. Show "EXCLUSIVE" badge in quality card when active.

**Files:** `app/build.gradle.kts`, `audio/SendspinAudioEngine.kt`, `cpp/audio_engine.cpp`, new `audio/NativeBridge.kt`

**Risk:** NDK toolchain in CI. Device fragmentation (not all devices allow exclusive mode). Buffer underrun handling.

#### 2. MA Loudness Readout
**What:** Show what Music Assistant's DSP pipeline is doing to the level — `loudness`, `loudness_album`, `volume_normalization_gain_correct` from `StreamDetails`.

**Why:** An audiophile wants to know if the server is normalizing their carefully-mastered FLAC. Currently the quality card shows the format but says nothing about gain manipulation.

**How:**
1. Parse `loudness` / `loudness_album` / `volume_normalization_gain_correct` from `MaParse.streamFormats()`.
2. Add to `StreamQuality` or a new `LoudnessInfo` model.
3. Show in the quality card: "MA normalization: −6.2 dB (album)" or "No normalization".
4. Show whether gain correction is active (output format ≠ input format in DSP).

**Files:** `ma/MaModels.kt`, `audio/StreamQuality.kt`, `ui/screens/NowPlayingScreen.kt`

#### 3. Crossfade (Navidrome Path)
**What:** Configurable crossfade between tracks on the ExoPlayer path.

**Why:** Gapless is correct for albums, but a crossfade option is what every DJ-mix and party playlist needs. ExoPlayer supports this natively.

**How:**
1. Add a crossfade duration setting (0 = off, 1–12 seconds).
2. Use ExoPlayer's `CrossfadeProcessor` or a custom `AudioProcessor` that overlaps the tail of one track with the head of the next.
3. Apply only when gapless would otherwise be silent (not within a continuous album).

**Files:** `audio/LocalPlayer.kt`, `data/AppSettings.kt`, `ui/screens/SettingsScreen.kt`

#### 4. Gapless on MA Path (Protocol Solution)
**What:** Solve the `stream/end` ambiguity — the same message means both "pause" and "track boundary."

**Why:** The #1 audio quality issue on the primary playback path. Every continuous album, live recording, and DJ mix has a gap between tracks.

**How:**
- **Option A (client heuristic):** After `stream/end`, watch for `server/state` with `playback_speed: 0` within a short window. If it arrives → pause (flush). If `stream/start` arrives first → track boundary (keep tail).
- **Option B (protocol extension):** Propose to the Sendspin spec that `stream/end` carry a `reason` field. Client-side only, can't control the server.
- **Option C (adaptive buffer):** Reduce the read-ahead buffer from 4 MB to ~500 KB. Less tail to discard on pause, but more vulnerable to network jitter.

**Recommendation:** Option A — it's the only one entirely in our control and doesn't sacrifice buffer resilience.

**Files:** `audio/SendspinAudioEngine.kt`, `service/Playback.kt`

#### 9. Warm Reconnect
**What:** Send `client/goodbye` with `reason: "restart"` when the app is backgrounded, so MA holds the player slot for 30 seconds.

**Why:** A quick app switch (reply to a message, check a notification) currently drops the player from MA's speaker list. Other speakers in the group see it disappear and may adjust. Warm reconnect keeps it alive.

**How:**
1. In `SendspinConnectionService.onTaskRemoved` or `onAppBackgrounded` (via `ProcessLifecycleOwner`), call `disconnect(reason = "restart")` instead of `"user_request"`.
2. On foreground return, reconnect — MA still has the slot.
3. Use `ProcessLifecycleOwner` for app-level lifecycle, not Activity-level.

**Files:** `service/SendspinConnectionService.kt`, `service/Playback.kt`, new `AppLifecycleObserver.kt`

#### 12b. Toggleable Background Connection (TTS Battery Saver)
**What:** A setting to control whether the Sendspin connection service stays alive permanently for TTS/announcements, or only runs during active playback.

**Why:** `SendspinConnectionService` holds `PARTIAL_WAKE_LOCK` + `WIFI_MODE_FULL_LOW_LATENCY` from `onCreate` to `onDestroy`. This is intentional — HA TTS announcements arrive like any other MA player event, and the socket needs to be open to receive them. But a user who doesn't use TTS (or who is on mobile data and wants to save battery) is paying for a permanent foreground service, wake lock, and wifi lock for nothing.

**How:**
1. Add `keepAliveForAnnouncements` setting (boolean, default `true`) to `AppSettings`.
2. In `SendspinConnectionService`, when the setting is `false`:
   - Don't call `startForeground` on connect — only start the service when `Playback` is actively playing.
   - Stop the service (and release locks) when playback goes idle, rather than keeping it alive.
   - The `SendspinService` media notification still works — it's a separate service.
3. When `true` (default): current behavior — service stays alive, TTS works, socket persists.
4. Setting goes under **Settings → Servers → Music Assistant → Keep alive for announcements**.
5. Changing the setting reconnects (stops the connection service, starts it under the new mode).

**Trade-off:** Disabling this means HA TTS announcements won't play through the phone while the app is backgrounded. The setting description should say this clearly.

**Files:** `data/AppSettings.kt` (new setting), `service/SendspinConnectionService.kt` (conditional keep-alive), `service/Playback.kt` (start/stop service based on setting), `ui/screens/SettingsScreen.kt` (toggle)

#### 12c. Direct Hue Bridge Connection (Light Sync without HA)
**What:** A direct connection from the app to the Philips Hue Bridge, running the syncoV2 music-reactive algorithm on-device. No Home Assistant, no syncoV2 integration, no HA entity required.

**Why:** Today Light Sync requires HA + syncoV2 + an HA `media_player` entity. That means:
- It doesn't work with the local/Navidrome player (no entity to follow).
- It doesn't work for users who don't run Home Assistant.
- It's limited by entity update latency (seconds, not milliseconds).

Direct mode cuts the entire HA path out:
```
Today:  App → HA WebSocket → syncoV2 → Hue Entertainment API → Bridge → Lights
Direct: App → Hue Bridge Entertainment API (DTLS/UDP) → Lights
```

And it's *better* than the current path, because the app has the decoded PCM audio in its hands:
- **Real-time beat detection** from the audio stream (not from entity state updates every few seconds).
- **Real-time FFT / frequency analysis** for per-band energy (bass, mid, treble → different lights).
- **Sub-second light response** — the audio is right there, no round-trip through HA.
- **Works on both backends** — MA path (tap `SendspinAudioEngine` decode loop) and Navidrome path (ExoPlayer `AudioProcessor` chain).
- **No HA dependency** — works for users who have a Hue Bridge but no Home Assistant.

**Architecture:**

The feature has four components:

1. **Hue Bridge Discovery + Auth** (`hue/HueBridgeClient.kt`)
   - mDNS discovery: `_hue._tcp` on the LAN (the bridge advertises itself).
   - Authentication: the Hue Bridge "link button" flow — user presses the physical button on the bridge, the app sends a POST to `/api` with a device type, the bridge returns an API key. Store it encrypted (same Keystore path as other credentials).
   - REST API: get lights, groups (entertainment areas), scenes, capabilities.
   - The bridge's REST API is plain HTTP on port 80 (LAN-only by design).

2. **Hue Entertainment Streaming** (`hue/HueEntertainmentStream.kt`)
   - The Entertainment API uses **UDP with DTLS** (AES-128-CBC, PSK derived from the bridge's API key + a client key exchanged during setup).
   - The app opens a DTLS UDP socket to the bridge on port 2100.
   - Streams messages at 25–50 Hz, each carrying per-light color values (HSV or RGB) for every light in the entertainment area.
   - The protocol supports up to 20 channels per message (the Hue spec limit).
   - Android's `DatagramSocket` + a lightweight DTLS implementation (or BouncyCastle/SpongyCastle for DTLS).

3. **On-Device Synco Engine** (`hue/SyncoEngine.kt`)
   - Port of syncoV2's core music-reactive algorithm from Python to Kotlin.
   - Components to port:
     - **Beat detection** — energy-based onset detection from the audio tap.
     - **Color cycling** — cycle through the 16 preset color schemes (already defined in `LightSyncRepository.PALETTES`) based on beats and energy.
     - **Intensity ladder** — map energy level to brightness/intensity (subtle → medium → high → intense → extreme).
     - **Effects** — "music" (beat + frequency choreography), "movies" (calm brightness following), "fireworks" (bursts on big beats).
     - **Tunables** — reactivity, glow, movement, contrast, color speed, loudness (same keys as syncoV2's `const.TUNABLE_KEYS`).
     - **Dynamic colors** — album art extraction (already have `AlbumPalette`), song-derived colors.
   - The algorithm runs at audio frame rate (~48 kHz / 1024 samples = ~47 Hz), matching the Entertainment API's max update rate.

4. **Audio Analysis Tap** (`audio/AudioAnalysisTap.kt`)
   - For the **Navidrome path**: an ExoPlayer `AudioProcessor` that sits in the render chain, receives PCM non-blocking, and feeds an FFT + energy window to the Synco engine.
   - For the **MA path**: a tap in `SendspinAudioEngine.runLoop()` that copies decoded PCM to the analysis pipeline before writing to the AudioTrack.
   - The tap must be zero-overhead when Light Sync is off — no allocation, no copy, no FFT.
   - FFT: a radix-2 FFT on 1024-sample windows (or a Goertzel filter for specific frequency bands, which is cheaper if only bass/mid/treble are needed).

**Mode selection:**

| Mode | When | How |
|---|---|---|
| **A — Through HA (current)** | HA + syncoV2 configured, MA player active | App → HA WebSocket → syncoV2 → Bridge. Unchanged. |
| **B — Direct, MA player** | Hue Bridge configured, no HA needed | App taps `SendspinAudioEngine` PCM → on-device Synco → DTLS → Bridge |
| **C — Direct, local player** | Hue Bridge configured, Navidrome/offline active | ExoPlayer `AudioProcessor` → on-device Synco → DTLS → Bridge |

Mode follows the active player and the user's configured connections — same auto-selection principle as Mode B in the improvement roadmap, no manual toggle. If HA + syncoV2 is configured AND the user prefers it, Mode A stays. If the user has a Hue Bridge but no HA (or wants lower latency), direct mode takes over.

**Setup flow:**
1. Settings → Servers → Hue Bridge → "Discover bridges" (mDNS scan).
2. Tap a discovered bridge → "Press the link button on your bridge" prompt.
3. App sends auth request → gets API key → stores encrypted.
4. App fetches entertainment areas (groups of type "Entertainment").
5. User picks an area → Light Sync is now direct.

## 7. Architecture Observations

### Strengths
- **Pure Kotlin protocol layer** — JVM-testable, no NDK dependency for the common path. The architecture decision to avoid Rust/JNI was correct.
- **Ordered inbox** — the single-consumer `Channel<Inbound>` for text + binary is the right pattern for wire-ordering. Well-documented.
- **Process-scoped state** — `Playback`, `LocalPlayer`, `DownloadManager` all live on `SendpinApp`. Survives Activity/ViewModel destruction.
- **ExoPlayer for Navidrome** — the right choice. Gapless, exact seek, float output, audio focus, becoming-noisy — all delegated to a battle-tested framework.
- **ReplayGain as scalar** — not a DSP stage. A constant per-track gain is just a multiply. No buffer copy. Correct and efficient.
- **Credential encryption** — Android Keystore, AES-256-GCM, legacy fallback. Well-designed.

### Weaknesses
- **No DI** — `AppSettings(context)` constructed in 4+ places. Each creates its own DataStore access. Not a bug (DataStore is a singleton per name), but a smell.
- **Large files** — `SendspinAudioEngine.kt` (920 lines), `Playback.kt` (730), `MaRepository.kt` (791), `SubsonicClient.kt` (773). Each does a lot, but splitting would improve readability.
- **No integration tests** — the audio path, service lifecycle, and UI are only tested manually on device. The release notes repeatedly say "not verified on device."
- **JSON index for downloads** — works for small libraries, but doesn't scale. No search, no sort, O(n) lookups.
- **Native code is dead weight** — 505 lines of C/C++ in the repo, not compiled, not called. Either enable it or remove it.

### Patterns to Preserve
- **Documented "why"** — every non-obvious decision has a comment explaining why, not what. This is the codebase's greatest strength. Preserve it.
- **Pure functions for testable logic** — `HeadGate`, `StreamContinuity`, `Scheduling`, `SyncGate`, `ReplayGain`, `FormatNegotiator` are all pure objects. JVM-testable. Keep this pattern.
- **Corrections section** — the improvement roadmap has a "Corrections" section documenting where earlier analysis was wrong. This is excellent engineering culture. Keep it.

## 9. Security Review

### Good
- Credentials encrypted at rest with AES-256-GCM via Android Keystore.
- Subsonic token auth (password + salt → MD5). Password never on URL.
- HA long-lived token encrypted.
- No hardcoded API keys or secrets.

### Could Improve
- **No `network_security_config.xml`** — the app connects to LAN servers over cleartext. Android's default allows this for `minSdk 31`, but an explicit config that allows cleartext only for private IP ranges and requires TLS for public hosts would be safer.
- **No certificate pinning** — for users who expose MA/Navidrome over the internet with TLS, certificate pinning would prevent MITM. Low priority for a LAN-first app.
- **Crypto fallback to plaintext** — `Crypto.encrypt()` falls back to plaintext if Keystore is unavailable. This is documented as "never lose the value," but it means a device with a broken Keystore stores passwords in cleartext. Acceptable trade-off, but worth logging.

## 10. Summary

CAMusic v0.5.0 is a **remarkably mature app** for its version number. The protocol implementation is spec-accurate, the audio pipeline is genuinely audiophile-grade (24-bit, clock-synced, ReplayGain, USB DAC), and the codebase has a culture of documentation and correction that most commercial projects lack.

The biggest gaps are:
1. **UI for features that already have client-side support** (version picker, cross-device resume, format switching) — low-hanging fruit.
2. **The MA gapless problem** — the `stream/end` ambiguity is the one thing preventing truly seamless album playback on the primary path.
3. **Native AAudio** — the code exists, it just needs to be enabled and wired.
4. **Platform reach** — Android Auto, widgets, Quick Settings tiles would make the app a daily driver, not just an audiophile tool.

The recommended order is: **UI for existing client work first** (fast, high-impact), then **protocol work** (gapless, warm reconnect), then **platform features** (Auto, widget), then **native audio** (the big one).
