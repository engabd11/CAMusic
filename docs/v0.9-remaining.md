## How to read this

The v0.9 plan had **five load-bearing premises that did not survive contact with the source**, and
every one of them was found by checking rather than by building:

| Claim | Reality |
|---|---|
| 0.2's "player is not available" was "not a code bug" | It was. A re-minted player id, captured in eight places. Re-selecting in Speakers *masked* it. |
| Reduced motion needs "a global multiplier in `Motion.kt`" | Compose already applies one. The real gap was `InfiniteTransition`, which suspends rather than ending. |
| 0.5 was fixed by a 1px visibility threshold | It removed ~300ms of a ~780ms tail. ~490ms is still "stuck". |
| Predictive back is "~20+ sites, a mechanical sweep" | 11 sites — and the main one was a plain bug: back had *no* animation at all. |
| Real glass = "extend the `Modifier.blur` infrastructure" | `Modifier.blur` blurs the composable it is applied to. On a card, it blurs the card's own text. |

So each item below carries an explicit confidence marker. **Verified** means someone read the code
or the dependency's source and quotes it. **Assumed** means it sounds right and nobody has checked.
Treat *Assumed* as a task to verify first, not a task to start building.

## Priority 0 — On-device verification

### DONE for the playback chain — confirmed on hardware, 2026-08-16

A release build of `master` (#54 + #55 + #56, commit `ad8de40`) was installed on the S23 and run.
**Music Assistant playback produces audio.** That clears, in a single run, everything Phase 0 had
been fixing without ever seeing a device:

- **`stream/start` arrives**, so the target player is right and **0.2c's re-minted player id is
  fixed** — the whole premise of #54.
- **The data source opens and the FLAC header parses**, so 0.2b's 42-byte `codec_header` fix holds.
- **The player reaches `READY` at `volume=1.0`, unmuted** — so not the sync gate, not audio focus,
  not device volume. `STREAM_MUSIC` measured 13/15 and unmuted.
- **No `Session ID must be unique`** in the crash buffer: 0.1 holds.
- 0.2's bounded retry was observed recovering cleanly (`IDLE → BUFFERING → READY`) rather than
  spinning.

**This unblocks Phase 1 and Phase 2**, both of which were waiting on exactly this.

The same session then found five further bugs, all on the MA path, **all fixed and all confirmed
working on the device** (PR #58): direct light sync not noticing MA; pause taking the server's ~30 s
read-ahead to fall silent; two connects racing into an orphaned socket that fought itself at the
reconnect interval; the local player's focus grab leaving the MA engine permanently deaf; and the
ambient idle show lost for MA. Four of the five share one shape — see **item G**, which is the
structural note they add up to.

Still owed a pass: 0.3 (volume), 0.7 (wedged process), the battery exemption, and Phase 1's own
checklist. The remaining verification for #55/#56 is visual and listed in those PRs.

### The diagnostic gap it exposed

The `first write:` line added in #54 lives on `SendspinAudioEngine`'s tag — the **default** engine.
That session ran on `SendspinExoEngine`, so the single most useful line never appeared and the
diagnosis had to come from `AAudio` and `dumpsys audio` instead. **The Exo/Oboe path needs the
equivalent one-line-per-stream "audio reached the output" log**, carrying gain and route, or the
next occurrence costs the same detour. Small, and worth doing before the next device session.

## A — Shared-element flight into Now Playing → **DONE (#61)**

Built as **A1**, and the diagnosis below held: the blocker was a missing scope, not missing
motion code. Two things had to move that this document did not anticipate:

- **`SharedTransitionLayout` had to move out too.** It wrapped only the NavHost. Two elements can
  only be shared inside one of these, and the *near* end of this flight — the mini bar — is
  bottom chrome, a sibling of the NavHost rather than inside it. Wrapping the overlay alone would
  have supplied a scope with nothing to fly from.
- **The key is a constant, not `art-<itemId>-<provider>`.** In the overlay layout the mini bar is
  on screen at the same time as the library grid, so an item-keyed bar collides with the grid tile
  of whatever is playing whenever that album is visible. The bar and the cover always show the
  same artwork, so they need no item identity to agree on. This is also why the "grid tile → Now
  Playing" case at the end of this item was not built: tapping a track does not navigate anywhere,
  so there is no transition to animate, and an item key that could animate it is exactly the one
  that collides.

**The "risk to check first" below resolved the other way**, and the workaround stays: the wrapper
is configured `ExitTransition.None`, and an exit of no duration holds nothing through. The
`onCollapse()`-after-settle gate is still load-bearing and now carries a comment saying it was
checked.

**Not yet judged on device** — this is the one item whose result is purely visual.

### The original analysis, kept because the above reads against it

**Confidence: verified.** Phase 3's last unshipped visual item.

`sharedArt` needs two composition locals (`ui/design/SharedTransition.kt`):

```kotlin
val shared = LocalSharedTransitionScope.current ?: return this
val animated = LocalNavAnimatedScope.current ?: return this
```

`LocalSharedTransitionScope` comes from the `SharedTransitionLayout` wrapping the NavHost, so it is
available. `LocalNavAnimatedScope` is the `AnimatedVisibilityScope` a NavHost `composable {}` block
supplies — and **Now Playing is not a nav destination.** It is a bare `if (overlayExpanded)` branch
in `App.kt`. So `sharedArt` on the overlay's cover either no-ops or, worse, matches against the
scope of whatever destination is underneath.

### Option A1 — wrap the overlay in `AnimatedVisibility` (try this first)

`AnimatedVisibility`'s content lambda receiver *is* an `AnimatedVisibilityScope`. So:

```kotlin
AnimatedVisibility(visible = overlayExpanded, enter = EnterTransition.None, exit = ExitTransition.None) {
    CompositionLocalProvider(LocalNavAnimatedScope provides this) { NowPlayingOverlay(...) }
}
```

Two things recommend it beyond being small:

- The overlay already owns its own enter/exit motion through `dragPx`/`settleTo`, so it wants
  `EnterTransition.None`/`ExitTransition.None` — the wrapper is there to supply a scope, not
  animation.
- **It may also delete a workaround.** `onCollapse()` is currently gated on `settleTo` returning,
  because releasing earlier lets the parent drop the composable mid-slide (`NowPlayingOverlay.kt`
  records this). `AnimatedVisibility` keeps its child composed through the exit, which is exactly
  the problem that gate exists to solve. Worth checking whether the gate can go.

**Risk to check first:** `ExitTransition.None` may remove the child immediately rather than holding
it. If so, use a zero-duration `fadeOut(tween(0))`, or hold visibility until the settle completes.

### Option A2 — promote Now Playing to a nav destination

Bigger, and it changes back-stack semantics and the mini-bar relationship. Only if A1 fails.

**Then:** the flight itself is `sharedArt(key)` on the mini bar's art and the overlay's cover with a
matching key, plus the grid tile → Now Playing case for tapping a track.

**Critical files:** `ui/App.kt` (the `if (overlayExpanded)` branch), `ui/screens/NowPlayingOverlay.kt`,
`ui/design/SharedTransition.kt`, `ui/screens/MiniPlayerBar` (in `App.kt`'s bottom chrome).

## B — Wide gamut (Display P3) → **DONE, half of it descoped (#61)**

`Window.setColorMode(COLOR_MODE_WIDE_COLOR_GAMUT)` is in, gated on the display actually having
one. **The extraction half was deliberately not built**, and the reason is worth recording
because this document argued for it:

The verified blocker below is correct — `getPixels` returns sRGB whatever the bitmap's colour
space. The fix proposed for it (an F16 decode read back through `copyPixelsToBuffer` or
`getColor`) would have worked and would have found **nothing to read**. Cover art reaches this
app from Music Assistant, Navidrome and Jellyfin as JPEG, which is sRGB in practice. Widening the
pipeline to carry values the source never contained is work with no output.

The gamut worth widening is the one the app *paints* into, and that is one line.

**What actually made album colour better was not this item at all.** The palette read wrong for a
reason neither this document nor the plan had considered: the OKLab lift pinned every accent to a
single perceptual lightness. That is defensible in the abstract and was the fade — sRGB's red
lives at L 0.63 and its blue at 0.45, so one target for all of them asked both to be lighter than
they can be *and* cut the chroma they could hold on the way. Green sits at 0.87 and was barely
touched, which is exactly why greens looked right and everything else looked washed. See #61.

### The original analysis

**Confidence: mixed — the blocker is verified, the fix is assumed.**

Reordered behind colour *accuracy* on the owner's judgement, which was right: the palette read
wrong because the lift ran in HSL, not because the gamut was narrow. That shipped in #55, so this
is now a genuine enhancement rather than a fix.

**Verified blocker:** `Bitmap.getPixels()` returns sRGB regardless of the bitmap's colour space, so
`paletteOf` cannot see wide-gamut values at all today. Widening the pipeline downstream of it would
change nothing.

**Assumed, needs checking before starting:**
- That Coil 2.7 exposes no colour-space setter on `ImageRequest` (it does have
  `bitmapConfig(RGBA_F16)`, which is the likely route — F16 preserves extended range).
- That reading F16 pixels means `copyPixelsToBuffer` + half-float decode, since `getPixels` is out.
- `Bitmap.getColor(x, y)` returns a colour in the bitmap's own space and would sidestep the buffer
  work, at 16k allocations per cover. Might be acceptable — this runs once per album on IO.

**Then:** a P3-aware `rgbToOklab` (the matrix in `AlbumPalette.kt` is sRGB primaries), and
`Window.setColorMode(COLOR_MODE_WIDE_COLOR_GAMUT)` in `MainActivity`.

**Judgeable only on a P3-capable display.** On anything else this is invisible by definition.

## C — MA-path gapless

**Confidence: verified, and reframed by the owner.** Deliberately last.

Music Assistant does not model gapless as its own concern server-side — it treats it as the same
mechanism as crossfade, which is why MA player apps expose a *crossfade* setting (disabled /
standard / smart) rather than a gapless one. **There is no server-side switch to ask for: true
gapless is client-side work in this app.**

That splits the item in two, and the plan only ever described the first half:

1. **Detection** (designed, not built). `stream/end` is byte-identical for "paused" and "track
   boundary". After it, watch for `server/state` with `playback_speed: 0` inside a short window →
   a pause, so flush; if `stream/start` arrives first → a boundary, so keep the tail.
2. **Joining** (not designed). Detection only tells the client which kind of `stream/end` it saw.
   Rendering the two streams without a seam is separate, and it is the part that has to be built
   rather than requested.

`SendspinAudioEngine` already keeps the codec and `AudioTrack` alive across a boundary
(`StreamContinuity`, `END_LINGER_MS`), so the groundwork is partly there — but `endOfStream()`
deliberately drops the buffer, because it has to handle pause correctly and cannot tell the two
apart. That is the exact knot (1) unties.

**Sequenced last on purpose:** it touches the audio path stabilised in #54, and building a
seam-joining path on top of a stack still being verified makes any regression hard to attribute.

**Critical files:** `protocol/SendspinClient.kt`, `service/Playback.kt`,
`audio/SendspinAudioEngine.kt` (`endOfStream`, `StreamContinuity`), `audio/SendspinExoEngine.kt`.

## F — Oboe native output produces no audio → **handed off to `docs/oboe-investigation.md` (PR #59)**

**Still unresolved after three fixes, all retested on device.** The full evidence, the mechanism,
the remaining lead and the next measurement now live in their own document — this entry is a
pointer, so the queue stays readable.

**The short version:** `buffered == written` on every stall, so not one frame is ever consumed;
`latency=13472us` proves the DAC anchor is healthy, `underrun=0`/`disconnected=false` prove the
AAudio stream is; and `driftEma ≈ 11.57 days` says `intendedHead` is absolute-clock distance ahead
of the DAC. `onAudioReady` then inserts a whole callback of silence without advancing the read
position, for ever. The engine is correct for the input it is given; the input is wrong.

Three fixes shipped to `master` along the way — the `handleBuffer` contract violation, the
`CLOCK_BOOTTIME`/`CLOCK_MONOTONIC` mismatch at the JNI boundary, and the native counters that
produced every number above. **All three are genuine defects worth keeping. None was this bug.**

**Recommendation: leave `useOboeOutput` opt-in and off** and pick this up as its own piece. Nothing
depends on it, ExoPlayer-without-Oboe is confirmed working, and Phase 2 promotes the ExoPlayer
engine alone with Oboe explicitly left opt-in — so **F blocks nothing**.

**Still open regardless of root cause, and small:** the path fails *silently*, reporting a playing
player that emits nothing. The stall is now detected and not acted on; it should surface or fall
back to the platform sink.

### The original diagnosis, kept because the handoff reads against it

**What was wrong.** `OboeAudioSink.handleBuffer` returned `true` unconditionally, discarding what
the native write reported. That return value is the `AudioSink` contract's answer to "was this
buffer fully consumed", and `false` is what tells ExoPlayer to re-present it once the sink drains.
Answering `true` regardless has *two* consequences, and between them they account for both halves
of what the device showed:

- a ring that cannot take the audio drops it, silently; **and**
- `framesWrittenTotal` climbs past what was accepted, corrupting `getCurrentPositionUs`
  (written-minus-buffered) — and a pinned position is exactly what "stuck playing with no progress
  for 10000 ms" measures.

`SendspinNativeOutput.write` returns frames accepted, so the honest answer was available all along.
`handleBuffer` now rewinds to exactly what the ring refused, and only accepted bytes reach the tap.

**The measurements shipped alongside**, because the fix is plausible rather than proven and would
mask the real cause if it is wrong:

- `configured 48000/2ch/16-bit drift=…`, plus an error if the native start refuses;
- `first write: N frames accepted of M offered …` — the line the default engine has had since #54
  and this path did not, which is why the one session that hit it had to be diagnosed from `AAudio`
  and `dumpsys` instead;
- an error after 50 consecutive total refusals, naming the sink rather than leaving it to be
  inferred from a renderer timeout ten seconds later.

**On the next APK:** turn `useOboeOutput` on and play.
`adb logcat -s OboeAudioSink SendspinExoEngine`.

| What you see | What it means |
|---|---|
| Audio plays | Fixed. Promote per Phase 2's own sequencing, still one axis at a time. |
| `first write: …` but silence | Audio reached the ring; the fault is below it, in the native engine or the AAudio stream. |
| No `first write:` at all | Nothing was ever accepted — the ring is not draining, and the refusal error should say so. |

The user-facing half of F is still open either way: this path fails *silently*, reporting a playing
player that emits nothing. Whatever the retest says, it should surface the failure or fall back to
the platform sink rather than presenting a working-looking player. Not done here.

### Original diagnosis, kept for the retest

**Confidence: verified by bracketing on hardware.** The one genuine failure the device session
found, and the plan called it in advance: *"Oboe's native path has not been run on real hardware at
all — keep `useOboeOutput` opt-in for a later round."* It had been run now, and it does not work.

**Bracketed by the owner, three-way:**

| `useExoPlayerForSendspin` | `useOboeOutput` | Result |
|---|---|---|
| on | **on** | **No audio.** Player reports playing. |
| on | off | **Audio works.** |
| *(default engine)* | — | Known good, every prior release. |

So the fault is confined to `OboeAudioSink` and the native engine behind it. Nothing upstream is
implicated: same build, same stream, same track, one toggle apart.

**What the log shows.** The native side comes up entirely successfully —

```
AAudioStreamBuilder_openStream() returns 0 = AAUDIO_OK
AAudioStream_requestStart(s#6) returned 0            (state 3 → 4, started)
AudioPlayerStateMonitor: Found a new active media playback ... type:AAudio ... state:started
AAudioFlowGraph: configure() source format = 0x00000001 (PCM_I16), channels = 2, rate = 48000
```

— and then ExoPlayer gives up on it:

```
SendspinExoEngine: playback state = READY
SendspinExoEngine: isPlaying = true (volume=1.0)
SendspinExoEngine: player error: ERROR_CODE_TIMEOUT
  Caused by: Player stuck playing with no progress for 10000 ms
```

A started stream, an unmuted sink at full gain, no sound, and a position that never advances.

**Prime suspect, found by reading rather than measured.** `OboeAudioSink.handleBuffer` discards the
native write's return value and returns `true` unconditionally. `AudioSink.handleBuffer` must return
`false` when it could not consume the buffer, so ExoPlayer retries — returning `true` regardless
means a full ring silently drops audio while `framesWrittenTotal` keeps climbing. Since

```kotlin
getCurrentPositionUs() = (framesWrittenTotal - nativeOutput.bufferedFrames()) / sampleRate
```

that also plausibly pins the reported position, which is exactly what "stuck playing with no
progress" measures. **Plausible, not proven** — it explains both symptoms from one cause, which is
suggestive and not conclusive. The native ring's fill/drain behaviour has not been instrumented.

**Do first, before any fix:** add the missing "audio reached the output" log to this path (see P0's
diagnostic-gap note) and log what `nativeOutput.write` actually returns versus what was asked. That
turns "plausible" into "measured" for the cost of two lines.

**Also worth doing regardless of the cause:** the toggle currently fails *silently* — playback
reports playing, and the only user-visible consequence is no sound. Whatever the fix, this path
should either surface the failure or fall back to the platform sink rather than presenting a
working-looking player that emits nothing.

**Bearing on Phase 2:** none, and that is worth stating. Phase 2 promotes `useExoPlayerForSendspin`
only, with `useOboeOutput` explicitly left opt-in — which the plan already specified, and which this
result vindicates. Phase 2 is not blocked by F.

**Critical files:** `audio/OboeAudioSink.kt` (`handleBuffer`, `getCurrentPositionUs`, `configure`,
`play`), `audio/SendspinNativeOutput.kt`, `cpp/sendspin_output_engine.cpp`.

## E — Driving overlay: control music without leaving the map → **DONE (#61)**

Both decisions were settled the way this document recommended, and **both mechanisms were built**
rather than one: **E2 (Picture-in-Picture) is the default**, because no permission at all is a
large win for something set up once in a car park, and **E1 (`SYSTEM_ALERT_WINDOW`) is behind it**
in Settings for the driving-sized targets PiP cannot give. The trigger is the car's Bluetooth,
with a Quick Settings tile and a Settings switch beside it, and the bar is always gated on
playback.

The `ComposeView` view-tree-owner gotcha was budgeted for and is handled —
`DrivingOverlayService` is a `LifecycleOwner`, a `SavedStateRegistryOwner` and a
`ViewModelStoreOwner`.

**One thing this document did not anticipate:** transport routing had to move onto
[`PlaybackOwner`](#g). `SendspinService.route` chooses between this phone's Sendspin stream and a
remote MA speaker and does *not* know about the local player, because the shade it serves is
never showing one. Anything outside the shade has all three cases, and a control that pauses the
wrong player while someone is driving is the worst possible place for that to be got wrong. So
`playPause`/`next`/`previous` now live on the authority that already knows who owns the session —
which is item G paying for itself in the first feature built on top of it.

**Still to check on device, and it is the one that could invalidate E2:** Android 12+ lets an app
call `setHideOverlayWindows(true)`. Whether Google Maps does this in navigation mode is still
**assumed not**. If it does, E1 becomes the plan rather than the upgrade — the code for that is
already there, it would only change which is the default.

### The original analysis

**Confidence: mixed.** The reuse is verified; the two hard parts (which window mechanism, and what
turns it on) are flagged below and are the ones to settle before building.

**The problem, in the owner's words:** a lot of cars have no Android Auto. The phone sits in a
cradle running Google Maps, and changing a track means leaving the map, finding the app, hitting a
small target, and going back — while driving. That is genuinely dangerous, and it is the one item
in this queue that is a *safety* feature rather than a polish or correctness one. It should be
weighted accordingly.

**The shape:** a slim always-on-top bar along the bottom edge, over whatever is on screen, with a
small number of very large targets — previous / play-pause / next, and the current track's title.
Nothing scrollable, nothing that needs reading, nothing that needs precision.

### What it can reuse (verified)

More than it looks like. The transport layer is already player-agnostic and process-scoped:

- `MaNowPlaying` is built once on `SendpinApp` and exposes `now: StateFlow<Now?>` — title, artist,
  artwork, playing state, and `isSelf`. It already survives the Activity dying.
- `SendspinService.route(localAction, remoteAction)` already picks between this phone's own stream
  (`pb.onPlayPause()` / `onMediaNext()` / `onMediaPrevious()`) and a remote MA speaker
  (`ma.playPause()` / `next()` / `previous()`). An overlay binds to exactly the same two calls and
  inherits correct behaviour for both cases for free.
- `LightSyncTileService` is precedent that this project already ships a Quick Settings tile, which
  matters for the trigger question below.

So the overlay is a *view* problem, not a playback-plumbing problem. That is the good news.

### Decision 1 — which window mechanism (settle before building)

**Option E1 — `SYSTEM_ALERT_WINDOW` overlay.** `TYPE_APPLICATION_OVERLAY` through `WindowManager`,
gated on `Settings.canDrawOverlays()` with a trip to `ACTION_MANAGE_OVERLAY_PERMISSION` to grant it.
Full control of size, position and target sizes. The conventional answer, and the only one that
gives a genuinely custom bar.

- **Gotcha, and it bites everyone once:** a `ComposeView` in a `WindowManager` overlay crashes
  unless the view tree is given a `LifecycleOwner`, a `SavedStateRegistryOwner` and a
  `ViewModelStoreOwner` (`setViewTreeLifecycleOwner` and friends). The service hosting the overlay
  has to supply all three. Budget for it; it is not hard, it is just invisible until it throws.
- **Risk to verify:** Android 12+ lets an app call `setHideOverlayWindows(true)` to suppress
  non-system overlays over itself. Whether Google Maps does this in navigation mode is **assumed
  not** and should be checked on-device *first*, because if it does, this whole approach is dead
  and E2 becomes the plan rather than the fallback.
- **Distribution note:** `SYSTEM_ALERT_WINDOW` is a sensitive permission under Play policy. This
  app ships on a debug keystore by design (see the README), so that is not a blocker today, but it
  would become one if D6 ever happens.

**Option E2 — Picture-in-Picture.** Costs no special permission at all. `PictureInPictureParams`
takes `RemoteAction`s, so play/pause/next/previous are expressible, and a PiP window floats over
other apps including Maps. Genuinely worth prototyping *before* committing to E1, because "no
permission prompt" is a large usability win for a feature someone sets up once in a car park.

- Limits: a small fixed window, a capped number of actions, easy to dismiss by accident, and
  entering PiP requires the activity to be foreground at the moment it enters — so the flow is
  "open the app, then start navigating", not "start it from anywhere".

**Option E3 — bubbles.** Investigated and rejected rather than omitted: `Notification.BubbleMetadata`
needs a conversation shortcut and a `Person`, and Android restricts bubbles to conversation
notifications. Not a fit for media.

### Decision 2 — what turns it on (recommendation: don't detect Maps)

The obvious framing is "show it when Google Maps is foreground", and that is the expensive path:
reading the foreground app needs either `PACKAGE_USAGE_STATS` (a special grant through a Settings
screen) or an `AccessibilityService` (heavyweight, and the most policy-sensitive permission on the
platform). Both are large costs for a detail the feature does not actually depend on.

**The requirement is "control music without leaving the map", not "know that Maps is running".** So:

- **Recommended trigger — the car's Bluetooth.** When the phone connects to the bonded device the
  user nominates as their car stereo, driving mode turns on; when it disconnects, off. That is
  exactly the situation being solved for, it is a single runtime permission (`BLUETOOTH_CONNECT`),
  and it needs no foreground-app inspection at all. A one-time "which of these is your car?" picker
  in Settings, listing bonded devices.
- **Manual fallback and override —** a Quick Settings tile, alongside the existing
  `LightSyncTileService`, plus a Settings switch. Covers a car with no Bluetooth pairing, an aux
  cable, or a user who simply wants it on.
- **Always gate on playback.** Never show the bar when nothing is playing, whatever the trigger.

Detecting Maps specifically can stay a later refinement if it ever proves necessary; it should not
be a prerequisite.

### Design constraints (this is a driving UI, so these are requirements)

- **Targets far larger than the 48dp mobile minimum.** Android Auto's driver-distraction guidance
  is the reference point to design against, not phone-sized touch targets.
- Three controls at most. Previous / play-pause / next. No queue, no scrubbing, no browsing —
  anything that invites reading invites looking away.
- High contrast, large type, and a title that truncates rather than scrolls.
- Draggable to the other edge and dismissible, since a cradle's position varies and the bar must
  never sit over the map's own controls permanently.
- **Honour `LocalReducedMotion`** — a moving element in peripheral vision while driving is the
  worst possible place to ignore it.

### Suggested position in the queue

Independent of everything else here — it touches no audio path and no shared file, so it can be

## G — The two players share one process, and the code keeps forgetting → **DONE (#61)**

All four of the suggested items are built, as `service/PlaybackOwner.kt`.

**The one thing worth adding to the analysis below:** naming the states produced *two* owners, not
one, and that turned out to be the whole value of the exercise rather than a detail of it.
`soundOwner` answers "who is producing sound" — what the analysis tap and Light Sync must follow.
`sessionOwner` answers "who holds a session" — what the media notification must follow, because a
paused queue still owns the shade. Item 4 below asks for an audit of the `active` vs `playing`
distinction; a single `owner` property would have quietly picked one of them and reintroduced the
bug it was written to prevent. The two are deliberately asymmetric — local wins the session
question, Sendspin wins the sound question — and each site now names which it is asking.

Focus arbitration is internal: `LocalPlayer.startOutput` announces a takeover *before* calling
`play()`, because ExoPlayer requests focus inside `play()` and the loss reaches `Playback` before
`playing` has flipped — an arbitration reading the flow would have seen `false` and torn the
engine down anyway. A foreign app still gets the full teardown, which is right.

`release()` leaves a restartable object in `LocalPlayer` too now. Nothing reached that path, which
is exactly why it was worth doing: an unrecoverable `release()` is a trap for whoever adds the
first caller, and it fails silently.

**This item earned its keep immediately.** The first feature built on top of it (E) needed
transport routing across all three players, and had the authority not existed it would have grown
a fourth copy of the precedence rules.

### The analysis

**Confidence: verified, five times in one afternoon.** Not a feature. A pattern that produced
most of the bugs in the 2026-08-16 session and will keep producing them.

The app runs two players in one process: `LocalPlayer` (Navidrome/Jellyfin/local) and the Sendspin
path (`Playback` + an engine). They share the audio output, audio focus, the media session, the
analysis tap, and a single `client_id` with Music Assistant. Almost every rule about how they
coexist is written as a comment beside one of them, and enforced in exactly one place — so when a
second place needs the same rule, nothing says so.

Every fix in PR #58 was an instance:

| Bug | The rule, and where it wasn't |
|---|---|
| MA engine went permanently deaf | `LocalPlayer` requests `AUDIOFOCUS_GAIN`; `Playback` reads a permanent loss as "another app took over" and *releases* — but it was us, not another app |
| Two clients fought over one `client_id` | One connection per player id, enforced by MA, assumed by us in one place and raced in another |
| Light sync ignored MA | Three wirings needed to know MA can drive the tap; two did |
| Ambient idle show lost for MA | `active` (session) vs `playing` — the local half had it right, the MA half was written against the comment saying so |
| Pause played 20s on | "`stream/end` means drop the buffer" enforced in one engine, and the other borrowed only its conclusion |

The shape is always: **a rule holds in most places and is missing in one, with a comment beside the
miss that was true when written.** Individually each is a small fix. Collectively they say the
coexistence rules are folklore rather than structure.

**Worth doing, in rough order of value:**

1. **Name the states.** There is no single answer to "which player owns the output right now". It
   is inferred, differently, in `activeLightSyncSource`, `SendspinService.currentShade`,
   `MaNowPlaying.now`, `pauseForLocalPlayback`, and the direct-sync gate. One authority those five
   read would have prevented at least three of the five bugs above.
2. **Make focus arbitration internal.** Two components in one process should not evict each other
   through `AudioManager`. `pauseForLocalPlayback` already handles this collision deliberately from
   one side while the focus listener handles it destructively from the other.
3. **No irrecoverable teardown.** `release()` should leave an object that can start again. Fixed in
   `SendspinExoEngine`; worth checking the same is true elsewhere.
4. **Audit for the `active` vs `playing` distinction** wherever both players are compared — it has
   now been got wrong twice.

**Not a rewrite**, and not urgent in the way a broken player is. But **D1's refactor should be
sequenced after this**, or it will preserve the folklore in tidier files. This is the reason to do
it before, not after, more feature work.

**Suggested by the assistant rather than requested** — cut it if the individual fixes are enough.

**Critical files:** `SendpinApp.kt` (`activeLightSyncSource`, the direct-sync gate),
`service/Playback.kt` (`focusListener`, `pauseForLocalPlayback`, `connectToServer`),
`service/SendspinService.kt` (`currentShade`, `route`), `service/MaNowPlaying.kt`,
`audio/LocalPlayer.kt`.

### D1 — Split the three files everything else has to touch → **TWO OF THREE DONE (#62)**

    LibraryScreen.kt   1,457 -> 596   (+4 files)
    SyncoEngine.kt     2,121 -> 1,703 (+2 files)
    LibraryViewModel   2,424 -> 2,397 (+1 file)

**LibraryScreen split cleanly** and is very nearly a pure move — 892 deletions against 31
insertions, every one of the 31 a visibility keyword or a rename. A Compose screen is a pile of
top-level functions with no shared mutable state, which is exactly what makes it splittable.
**SyncoEngine** gave up its two pure-data halves — the mode presets and the palette — at 426
deletions against 1 insertion.

**`LibraryViewModel` cannot be split by moving code, and that is the finding this item should
carry from now on.** It is one class whose members share one pile of mutable state, and Kotlin has
no partial classes: there is no arrangement of files that separates `stack` / `_node` / `reload` /
`maRepo` / `source` / `_backend` from the forty functions that touch them. The only piece that came
out is the one owning something *other than* browse state — the track preview, which owns a real
`ExoPlayer`.

Reducing it further means **extracting collaborators**: a browse stack, a radio controller, a shelf
loader, each taking the three or four dependencies it actually needs. That is a design change, and
this item's own scoping line — "not a redesign, and not a rewrite of working code" — rules it out.
So the item is not "still open"; it is **waiting on a decision** that the file-split framing cannot
make. Either the scope widens to allow collaborator extraction, or 2,400 lines is accepted as what
this class is.

Two things the split surfaced that were invisible before:

- **A byte-identical `Shelf` composable in `ArtistDetailScreen.kt`**, hidden while both copies were
  file-private. Renamed rather than deduplicated, to keep the refactor to the files it was about.
- **Widening `private` to `internal` wholesale collides** with same-named privates in sibling
  screens. Only the declarations that actually cross a new boundary were widened, which is its own
  argument for the rest staying private.

### D5 — Glance home-screen widget → **DONE (#61)**

`androidx.glance:glance-appwidget`, the same three controls as the driving bar and the mini
player, routed through the same [`PlaybackOwner`](#g) — a widget addressing the wrong player would
be the mini bar's old bug on a surface with no way to see what it was doing.

"The easiest thing to pick up in isolation" was true, and it still had one real trap that only
`lintDebug` caught: reading `StateFlow.value` inside a Glance composable. `provideGlance` suspends
for as long as the widget has a session and Glance keeps the composition alive across it, so a
`.value` snapshot paints once and then sits there — a track change would not have repainted it,
and the `updateAll` after a transport action was quietly carrying the whole feature. Collected
properly, the widget is live rather than merely correct.

Worth generalising from: **`assembleRelease` does not catch this.** Its `lintVital` only reports
issues marked fatal, and `StateFlowValueCalledInComposition` is not one. CI runs
`:app:testDebugUnitTest`, `:app:lintDebug` and `assembleDebug`; local verification should run that
exact set rather than a superset that happens to miss a subset.
