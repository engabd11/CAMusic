> **Status update 3.** MA playback was still silent after 0.1/0.2/0.2b, and the cause was not in
> the audio path at all: the app was addressing a player id it had minted and then forgotten
> (**0.2c**, new). `PlayerIdentity` re-mints the Sendspin `client_id` on a rename; `Playback`
> re-read it, and eight other holders captured it once at construction. **This falsifies 0.2's
> "not a code bug" conclusion** — re-selecting in Speakers masked the bug rather than fixing it,
> which is precisely why it worked instantly and why it came back. Two further silent-failure
> paths were fixed alongside it (a teardown race in `SendspinAudioEngine`, a dropped write in
> `OboeAudioSink`), and the "playing but silent" shape is now legible in one logcat capture.
> Shipped in PR #54; **not yet confirmed on a device.**
>
> **Status update 2.** With 0.1 fixed, on-device testing surfaced two more layers behind
> "can't play on MA" that the original report couldn't distinguish: a stale/wrong
> **target-player selection** (not a code bug — see 0.2's update), and once that was
> corrected, a **real FLAC `codec_header` parsing bug** that made every MA stream fail
> immediately (0.2b, new). Both are recorded in detail below. The retry-bound fix from
> Status update 1 is confirmed working as designed against this exact failure — 5 bounded
> attempts and a clean give-up, not another 58-minute loop.
>
> **Status update 1.** Phase 0's confirmed items (0.1, 0.2, 0.4, 0.5, 0.6) shipped — see
> PR #54. Investigating them further, with the device still connected, also turned up a
> seventh issue not in the original report (0.7, a wedged process from a prior session
> surviving a plain app-close) and deepened 0.2's fix (the retry is now bounded, not just
> logged). 0.3 (volume) was investigated in real depth — `ShadePlayer`'s routing,
> `MaNowPlaying`'s state, `DeviceVolume` — and the design holds up everywhere it was traced;
> no code bug was found, so nothing was changed there. Read the per-item updates below before
> trusting the original "not yet confirmed" framing — several of those are now stale.

## Context

CAMusic (package `com.engabd.sendpin`) is a mature app (v0.8.8, ~141 Kotlin source files, 526 JVM
unit tests) with three roles: a Sendspin protocol player that registers with Music Assistant for
remote-controlled/grouped multi-room playback, a standalone library client (Navidrome/Subsonic/
Jellyfin/local files) with downloads, and a Philips Hue light-sync engine (through Home Assistant's
syncoV2, or direct-to-bridge). The ambition has grown past the original "sendspin player" scope:
the best audiophile Android player, a browsing experience as rich and premium as the album art and
OLED/HDR displays it runs on, and a direct Hue light sync that beats Spotify's.

This plan started as a forward-looking roadmap, built by reading every internal planning doc and
then verifying every load-bearing claim directly against source (the docs drift from the code in
both directions — some things marked "done" aren't reachable by real users, some marked "untouched"
already shipped). **While that roadmap was being finalized, the owner reported the app is currently
broken in several concrete, reproducible ways on v0.8.8, and connected a physical device (Samsung
Galaxy S23) so this could be diagnosed with real crash logs and live logcat instead of guesswork.**
That changed the priority order completely: a roadmap toward "world-class premium" is moot while
the app's core function — playing Music Assistant audio at all — doesn't work. **Phase 0 below is
therefore new, and every item in it is either a confirmed root cause (code + live device log, not
speculation) or an explicitly flagged hypothesis awaiting confirmation.** The rest of the plan
(Phases 1-5) is the original roadmap, renumbered to follow stabilization.

Three scoping decisions that shape Phases 1-5:
- Testing happens on a real device after cutting a release, not before — Phase 1 produces a
  concrete on-device checklist for that workflow.
- Verifying and promoting the new ExoPlayer+Oboe MA-playback engine to default is a near-term
  priority (also the reachability unlock for direct Hue sync on MA playback) — now gated on Phase
  0 actually fixing that engine first, since it's one of the two confirmed-broken paths.
- The HDR/OLED visual push starts with wide-gamut (Display P3) accent colors, not a full HDR
  gainmap pipeline.

## Phase 0 — Emergency stabilization (fix confirmed-broken playback, do this first)

Reported by the owner, all reproducing on v0.8.8 right now: MA playback doesn't work regardless of
the experimental-engine setting; phone volume changes reach the player but glitch back toward
100%, and in-app volume changes don't reach the phone; selecting Jellyfin and playing a song
crashes the app and it won't reopen until cache is cleared; the mini-player sticks for a second
when swiped down; and the MA timeline briefly jumps then snaps back on track start and on every
seek (Navidrome doesn't have this). Diagnosed against a connected device: `adb logcat -d -b crash`
and the main log buffer, cross-referenced with the exact source lines.

### 0.1 — FIXED: two services collide on the same MediaSession ID and crash the process

**Root cause, proven by direct code read + device crash log, not a guess.**
`SendspinService.kt:464` and `LocalPlaybackService.kt:86` each build a media3 session the same way:

```kotlin
mediaSession = MediaSession.Builder(this, player).build()   // no .setId(...)
```

Neither call sets `.setId(...)`, so both default to the same empty-string session ID. Media3
enforces that session IDs be unique **per process** — the second `MediaSession` constructed with a
colliding ID throws. The device's crash buffer shows exactly this, repeatedly, for both services:

```
IllegalStateException: Session ID must be unique. ID=
  at SendspinService.onCreate(...:59)          <- and separately, at other times:
  at LocalPlaybackService.onCreate(...:51)
```

Eleven crash-and-restart cycles were captured in under four minutes on-device (05:30:21-05:34:09),
alternating between the two services, each `RuntimeException: Unable to create service` killing
the whole process. This is almost certainly new since the media3-session migration (`0927786`) —
that commit is what gave `SendspinService` its own `MediaSession` for the first time;
`LocalPlaybackService`'s session predates it and presumably worked fine in isolation, but the two
now collide whenever both are constructed in the same process.

**Why this explains multiple symptoms at once:**
- **"Can't play on MA regardless of experimental setting"** — if `LocalPlaybackService`'s session
  already exists (e.g. from a prior local-playback attempt, or app state that keeps it alive) and
  the user then starts MA playback, `SendspinService.onCreate()` throws immediately — before any
  engine-specific code (old or new) ever runs. The failure is upstream of engine selection, so of
  course toggling the experimental setting doesn't change the outcome.
- **The Jellyfin crash that requires a cache clear** — `LocalPlaybackService` is the same service
  Jellyfin, Navidrome, and local-file playback all share. It crashed with the identical exception
  in the captured buffer. This is very likely not Jellyfin-specific at all — any local-playback
  start while a colliding session exists would trigger it. The "won't reopen until cache is
  cleared" symptom fits a process that keeps recreating both services on launch (e.g. an
  auto-reconnect/restore-state path) and hitting the same collision every time, until whatever
  state drives that recreation is cleared.

**Fix, shipped in PR #54:** each `MediaSession.Builder` now claims a distinct, stable
`.setId(...)` — `"sendspin"` and `"local"`. Small, low-risk, well-understood media3 requirement.

**Critical files:** `service/SendspinService.kt:464`, `service/LocalPlaybackService.kt:86`.

### 0.2 — FIXED (immediate part): unbounded retry storm in the experimental engine

**Root cause, proven by code read + 58 minutes of live device log, not a guess.**
`SendspinExoEngine.kt:129-134`:

```kotlin
private val playerListener = object : Player.Listener {
    override fun onPlayerError(error: PlaybackException) {
        Log.e("SendspinExoEngine", "player error: ${error.errorCodeName}", error)
        player.prepare()
    }
}
```

The code's own comment acknowledges the risk: retrying via `prepare()` is "enough as long as
whatever caused the error doesn't recur." On-device, it recurred — immediately, every time, for
the entire test session. The device log shows **311,760 repetitions** of:

```
E SendspinExoEngine: player error: ERROR_CODE_TIMEOUT
Caused by: Player stuck buffering with no progress for 600000 ms
```

firing roughly every 150-200ms, continuously, from 11:30:04 to at least 12:28:36 — **58 straight
minutes**, only stopping when the capture ended. This is a genuine busy-loop: `onPlayerError` →
`player.prepare()` → same stuck `SendspinDataSource` → same error → repeat, with no retry limit,
no backoff, and nothing resetting the underlying data source between attempts. The device log also
shows sustained GC pressure and repeated "long monitor contention... for 100-180ms" warnings on
the main thread throughout the window — this isn't just a silent log spam, it's actively costing
CPU, battery, and thermal headroom the entire time, while producing no audio and no user-visible
error state.

**A separate, open question this surfaces:** during that entire 58-minute window, the
`SendspinClient` protocol log shows only the periodic `rx server/time` heartbeat — no
`server/hello`, no `stream/start`, no `server/state` at all (confirmed by checking what
`SendspinClient` actually logs: everything except `server/time` goes through a log call that
would have appeared). The WebSocket connection to MA itself was healthy the whole time. That means
MA never actually dispatched a stream to this player during the whole test — which is either a
separate server-side/registration issue, or the play request never correctly reached MA in the
first place. **This needs a fresh, deliberately-logged repro** (reproduce with logcat capturing
from the moment "play" is pressed, not mid-session) to see whether `stream/start` ever arrives at
all — that's the deeper question behind why the engine had nothing to play in the first place.

**Fix, two parts:**
1. **Immediate — shipped in PR #54.** `onPlayerError` now counts consecutive errors and backs
   off (500ms/1.5s/4s/8s) instead of retrying instantly and unconditionally; `STATE_READY` resets
   the count, as does a fresh `start()`. After 4 consecutive failures it stops retrying entirely
   and calls a new `onFatalError` callback, which `Playback.kt` wires to `client?.reconnectNow()`
   — the same "the user asked for music" escalation `MaRepository.playMedia` already uses
   elsewhere, forcing a clean Sendspin reconnect rather than hammering a dead data source forever.
   This alone turns a battery-draining infinite loop into a bounded, user-visible failure,
   regardless of the deeper cause below.
2. **Root cause — resolved, and it was two separate things, neither the deep protocol mystery
   this originally looked like.** A fresh, logged repro after 0.1 landed showed `stream/start`
   genuinely never arriving — but the Sendspin connection itself was completely healthy the whole
   time (`server/hello` confirmed `player@v1` active, clock converged, `client/state:
   "synchronized"` reporting correctly per `SyncGate`). The play command itself was failing
   *before* it could ever cause MA to dispatch a stream, with a toast reading Music Assistant's
   own server-side error text verbatim (`LibraryViewModel.kt:1062`'s `_toast.tryEmit(e.message ?:
   "Couldn't play")`, fed from `MaApiClient.kt:183-184`, which passes MA's `"error"`/`"details"`
   JSON field straight through as the exception message) — "player is not available". The
   immediate cause was that `playTarget()`/`_targetPlayer` pointed at a player that was not this
   phone, and re-selecting in the Speakers screen fixed it on the spot.
   - ~~**Not a code bug** — `playTarget() = _targetPlayer.value.ifBlank { myPlayerId }` is the
     same correct-by-construction pattern used in `NowPlayingViewModel`/`MaNowPlaying`.~~
     **This conclusion was wrong; see 0.2c.** The pattern is correct, but `myPlayerId` was not:
     it was captured once at construction in eight places while the id it copies can be re-minted
     at runtime. Re-selecting in Speakers *masked* the bug — an explicit target bypasses
     `ifBlank { myPlayerId }` — which is exactly why it worked immediately and why the symptom
     came back later. This one is on the "no code bug found" call, not on the owner.
   - Still true, and still the reason the symptom was MA-only: Navidrome/Jellyfin play through
     `LocalPlayer` directly and never consult a target-player selection at all.
   - **Once that was fixed, a second, real bug surfaced** — see 0.2b below.
   - **Worth a UX follow-up, not filed as a bug here:** nothing prominently surfaces "you are
     currently controlling &lt;player X&gt;, not this phone" outside the Speakers screen itself,
     so a stale/unintended selection reads as "MA is broken" rather than "wrong target". A
     visible indicator (e.g. on Now Playing or in the MA server's own settings page) would have
     made this immediately obvious instead of costing a debugging session. 0.2c raises the value
     of this: it would have shown the wrong id being addressed, rather than leaving it to be
     inferred from an error string.

**Critical files:** `audio/SendspinExoEngine.kt` (`playerListener`, `MAX_CONSECUTIVE_ERRORS`,
`RETRY_BACKOFF_MS`), `service/Playback.kt` (`onFatalError` wiring at `startSendspin`),
`audio/SendspinDataSource.kt`, `protocol/SendspinClient.kt`, `ma/LibraryViewModel.kt:1056-1062`
(`playTarget`, the toast), `ma/MaApiClient.kt:175-186` (`handle`, where MA's error text becomes
`MaApiException.message`).

### 0.2b — NEW, FIXED: FLAC `codec_header` parsing rejected every MA stream

Surfaced immediately once 0.2's target-player fix let `stream/start` actually arrive: every MA
stream on the experimental engine failed instantly with

```
IOException: Sendspin FLAC stream: missing or malformed codec_header
(raw='ZkxhQ4AAACISABIAAAAAAEpYC7gC8AAAAAAAAAAAAAAAAAAAAAAAAAAA' decodedSize=42, want 34)
  at SendspinDataSource.kt:141
```

— confirming 0.2's retry bound works exactly as designed: 5 attempts with backoff, then a clean
"giving up after 5 consecutive errors without reaching STATE_READY" instead of another 58-minute
busy-loop.

**Root cause.** `SendspinContainerHeader.flacStreamHeader` assumed `stream/start.codec_header`
always decodes to the bare 34-byte FLAC STREAMINFO payload (so it could synthesize its own
`"fLaC"` magic + metadata-block header around it for ExoPlayer's `FlacExtractor` to sniff). This
Music Assistant server sends the *complete* header instead — magic (4 bytes) + block header
(4 bytes) + STREAMINFO (34 bytes) = 42 bytes exactly, matching the logged `decodedSize` precisely.

**Fix, shipped:** `extractStreamInfo()` now accepts either shape — bare 34-byte STREAMINFO, or a
42-byte buffer starting with the `"fLaC"` magic, sliced down to just the STREAMINFO payload
either way. Applied to **both** engines: `SendspinDataSource` (the experimental path, where this
was caught) and `SendspinAudioEngine.createFlacDecoder` (the *default* engine every real user is
actually on right now) — the default engine made the identical 34-byte assumption for its
MediaCodec `csd-0`, silently swallowing the mismatch in a bare `catch (_: Exception) {}` that is
now a logged warning instead. This was very likely about to become a much bigger problem: Phase 2
of this plan calls for promoting the experimental engine to default specifically because it was
believed proven; instead, this MA server would have failed *every single FLAC stream* the moment
that promotion shipped, on an engine already exercising 100% of users. Whether the default
engine's silent swallow ever actually produced audible failures in practice (as opposed to always
having a code path AOSP's decoder tolerates) is still unconfirmed — the warning log now added
will show a "csd-0 left unset" line if it ever hits the same mismatch on-device.

Two tests added (`SendspinContainerHeaderTest.kt`) for the new tolerance, including a guard
against a coincidentally magic-prefixed buffer of the wrong total size being sliced incorrectly.
528 tests pass total.

**Critical files:** `audio/SendspinContainerHeader.kt` (`extractStreamInfo`, new),
`audio/SendspinDataSource.kt:139-145` (updated error message), `audio/SendspinAudioEngine.kt:879-898`
(`createFlacDecoder`), `test/.../SendspinContainerHeaderTest.kt`.

### 0.2c — NEW, FIXED: the app plays to a player id it minted and then forgot

Reported after 0.1/0.2/0.2b shipped: MA playback still produces no audio. Found by reading the
*identity* path end to end rather than the audio path a fourth time — and it falsifies 0.2's
"not a code bug" conclusion above.

**Root cause.** `PlayerIdentity.newIdentity()` mints a new Sendspin `client_id`. It is the only
way to shake off a name Music Assistant has already committed to (MA keys a Sendspin player on
its `client_id` and keeps the name it was *first* registered under; the protocol has no rename
message), so it is not an exotic path: `Playback.enablePlayer` calls it whenever the wanted
player name differs from the last one MA confirmed — including the very common case where
`registeredPlayerName` is still blank because `syncPlayerConfig` never got its confirmation —
and `reregister` always does. Both are ordinary Settings actions.

`Playback` re-read the new id immediately. Nothing else did:

```kotlin
val myPlayerId: String = PlayerIdentity.getPlayerId(app)   // captured once, at construction
```

— in `LibraryViewModel`, `NowPlayingViewModel`, `SpeakersViewModel`, `MaNowPlaying`, and the
album, artist, playlist and DSP view models. After a re-mint, every one of them addresses the
*previous* player, which MA keeps as an unavailable entry rather than deleting:

- `playTarget() = _targetPlayer.value.ifBlank { myPlayerId }` sends `play_media` to the dead id.
  MA answers "player is not available" — **the exact toast 0.2 recorded and attributed to user
  error** — or, when the stale entry is still present, queues to a player that is not this phone
  and makes no sound. The app goes on showing something playing, because it is polling the same
  dead id.
- `MaNowPlaying.isSelf` compares against the dead id, so the media shade's entire
  local-vs-remote routing is wrong. This is the worst of the eight: `MaNowPlaying` is built once
  on `SendpinApp` and never rebuilt, so a stale id there persists for the whole process, across
  reconnects. Only a restart clears it — which is why the failure looked intermittent, and why
  force-stopping or clearing data appeared to help.
- `SpeakersViewModel.selectPlayer` normalises "this phone" to `""` by comparing against it, so
  picking this phone **persisted the old concrete id** as the target. That survives restarts and
  points every play command at the dead player until it is re-picked.

That last point is the whole shape of 0.2: an explicit target bypasses `ifBlank { myPlayerId }`,
so re-selecting in Speakers masks the bug for exactly as long as the stored selection happens to
be a live id — and it stops being one at the next rename.

**Fix, shipped in PR #54.** Every holder reads through `PlayerIdentity` rather than copying it,
`Playback.playerId` included (which removes the two hand-written re-assignments that kept it
right while eight other copies went stale). `PlayerIdentity.cachedId` is `@Volatile`, since a
rename clears it from one coroutine while view models, the Sendspin client and `MaNowPlaying`'s
poll read it from others. `MaNowPlaying` logs loudly when the persisted target names a player
the server does not have — deliberately a log and not an automatic reset, because a legitimate
speaker that is merely asleep drops out of `players/all` the same way.

**Two further silences found in the same pass, both fixed:**

- `SendspinAudioEngine`'s deferred teardown (2 s after `stream/end`) ran on a helper thread and
  raced `stream/start`. A track arriving in that gap either took `start()`'s continuation branch
  — which deliberately does not restart a worker, because a continuation normally leaves one
  alive, and this one had already left its loop — or built a fresh codec, track and worker that
  the helper then released underneath it. Either way: a connection that looks entirely healthy
  with nothing decoding. Teardown now happens on the worker itself, under the monitor,
  re-checking that no new stream claimed the engine first. `start()` is also split into two
  phases so `releaseInternal`'s join no longer runs while holding the monitor the worker needs
  in `ensureTrackFor` — that deadlocked until the join timed out, after which `start()` built a
  second worker on top of a live one, two decoders interleaving into one track.
- `OboeAudioSink.handleBuffer` skipped the write entirely when there was no current data source,
  having already drained the buffer and reported it handled: samples discarded with no log and
  no error. Reachable, since `SendspinExoEngine.flush()` clears the data source on
  `stream/clear` while decoded buffers can still be in flight.

**Diagnostics added,** because three different causes present identically as "playing, silent":
the engine choice is logged at connect; `SendspinAudioEngine` logs one line the first time PCM
reaches the track (rate, encoding, gain, route) and an error for a codec it cannot decode
(previously a silent `else -> null` that discarded every frame); `SendspinExoEngine` logs its
playback-state transitions, which separates "never prepared" from "stuck buffering" from
"running and silent downstream". One capture should now be enough to place any recurrence.

**Not yet confirmed on a device** — none was attached for the session that found this. The
mechanism is proven by reading; the reproduction is not. The check that matters: play from MA,
then rename the player in Settings → MA → player settings and play again *without restarting the
app*. That is the sequence that used to go silent.

**Critical files:** `discovery/PlayerIdentity.kt` (`getPlayerId`, `cachedId`),
`service/Playback.kt` (`playerId`, `enablePlayer`, `reregister`), `service/MaNowPlaying.kt`
(`myPlayerId`, `isSelf`), `ui/viewmodel/SpeakersViewModel.kt` (`selectPlayer`),
`ma/LibraryViewModel.kt` (`playTarget`), `audio/SendspinAudioEngine.kt` (`start`,
`tearDownIdleStream`), `audio/OboeAudioSink.kt` (`handleBuffer`).

### 0.3 — INVESTIGATED, no code bug confirmed: bidirectional volume sync glitch

Two symptoms reported: right after a fresh launch, the volume shown reads 0 and doesn't respond
to the hardware rocker; separately (an earlier report, possibly the same underlying issue in a
different connection state) phone volume changes reach the player but "glitch, trying to go back
to 100%". Reference point from the owner: the Navidrome/local player gets this right — it
correctly controls both the player and the device volume — so `LocalPlayer`'s working pattern is
the thing to compare `ShadePlayer` against.

**What was actually checked, in full, not just skimmed:**
- `LocalPlayer.kt:359`: `.setDeviceVolumeControlEnabled(true)` on a *real* `ExoPlayer` — media3
  handles the whole device-volume round-trip itself because the player is genuinely backed by
  `STREAM_MUSIC`. `ShadePlayer` can't use this: it's a `SimpleBasePlayer` facade with no real
  audio-rendering `ExoPlayer` behind it (it may be describing a remote MA speaker), so it has to
  hand-implement `handleSetDeviceVolume`/`handleIncreaseDeviceVolume`/`getState`'s device volume.
- `SendspinService.kt`'s `currentShade()` (the routing logic): `remote = ma.now.value`;
  `volume = if (remote.isSelf) deviceVolumePercent() else remote.volumeLevel`. The suspected gap
  was that `remote` could be a "half-empty" placeholder object in the idle state, misrouting
  volume to a phantom remote target — **this turned out to be wrong.**
- `MaNowPlaying.kt:97-119` (`now: StateFlow<Now?>`): confirmed by full read that `Now` is *never*
  a placeholder — the `combine` block returns `null` explicitly whenever the local player has a
  session, the target player isn't found, or `nowPlaying?.title` is blank. `remote` is therefore
  always either `null` or a genuinely populated, real player state. In the idle case `currentShade()`
  falls through to its local branch (`volume = deviceVolumePercent()`), which is correct.
- `DeviceVolume.kt`: reads/writes `STREAM_MUSIC` directly and freshly on every call (`read()` is
  not a cached value), registers a `ContentObserver` for external changes. This is the same class
  `LocalPlayer` uses successfully, so it is very unlikely to be the difference between the two
  paths.

**Conclusion:** the routing design holds up everywhere it was traced against the actual code
(not just the parts quoted in the original hypothesis above, which undersold `MaNowPlaying`'s own
null-handling). No speculative change was made — rewriting working, carefully-commented routing
logic without a confirmed bug risks breaking legitimate remote-speaker volume control for a
hypothesis that didn't survive a full read. Two real possibilities remain, neither confirmed:
a genuinely different/stale `targetPlayer` selection persisted from earlier testing (so the code
is correctly showing/controlling a remote speaker the user doesn't realize is selected), or
something timing-related that only shows up live (e.g. around player registration on a fresh
connect) that static reading can't surface.

**Next step:** a fresh, deliberately-logged repro is the only way forward here — capture logcat
from `adb logcat -c` immediately before reproducing, reload Settings → Servers to check what
`targetPlayer` is actually set to, and add temporary logging in `currentShade()` and
`setVolumePercent()` if the persisted-target explanation doesn't hold up. Retest only after
0.2c is confirmed working on-device: a stale `myPlayerId` made `currentShade()`'s `isSelf` read
false while this phone genuinely *was* the player, which routes volume down the remote branch —
so the "persisted-target explanation" traced here may well have been 0.2c seen from the volume
side, and there is no point pinning the volume behaviour against a broken identity.

**Critical files:** `service/SendspinService.kt` (`currentShade`, `setVolumePercent`),
`service/MaNowPlaying.kt` (`now`), `audio/DeviceVolume.kt`, `audio/LocalPlayer.kt:359` (reference
implementation).

### 0.4 — FIXED: MA-only timeline/seek glitch (long-standing)

On track start, the position briefly showed the target then snapped to 0 (or the reverse); on
seek, it briefly overshot then snapped to the target. Navidrome (ExoPlayer-driven, no separate
estimation layer) never showed this.

**Root cause, confirmed by reading the full position-tracking architecture, not just the
suspected files.** This is *not* a gap in freeze/optimistic-update protection generally — that
protection already exists and is more sophisticated than initially assumed:
`NowPlayingViewModel.kt`'s `PlayerPositionTracker` (`positions`) already freezes the bar around
every *user-initiated* seek and skip (`freezeForSeek`/`freezeForTrackChange` at
`NowPlayingViewModel.kt:573-587`, called from `seekOnServer`/`next`/`previous`), and
`Playback.positionMs` is deliberately fed *through* that same tracker for the case where this
phone is the actively-playing Sendspin player (`sendspinAuthoritative()`,
`NowPlayingViewModel.kt:1599-1607`) specifically so seeking and skipping behave. The gap that
protection leaves open is **a track ending and the next one starting on its own** — nothing in
the UI initiates that, so nothing was there to freeze in advance; `Playback.anchorProgress`
(`service/Playback.kt`) received the raw `server/state` push for it with no protection at all,
and a `server/state` describing the *outgoing* track arriving a beat after the one for the
*incoming* track (or vice versa) — each with a perfectly plausible, perfectly current
timestamp — is what produced the jump-then-snap.

**Fix, shipped in PR #54:** `anchorProgress` now tracks the `title|artist` key of the track it's
currently anchored to. The first `server/state` naming a *new* key is trusted immediately; any
reading still naming that same key within 600ms afterward is held rather than applied — it's far
more likely to be the old track's state catching up than new information. This is deliberately
the same philosophy as `PlayerPositionTracker`'s freeze (trust an anchor, hold the line against
contradicting updates for a bounded window), applied reactively since the client has no advance
notice of a natural transition the way it does for a user-initiated one.

**Still open:** lock-screen/Bluetooth-initiated skip and seek go through `Playback.onMediaNext()`/
`ShadePlayer`'s command handlers directly, bypassing `NowPlayingViewModel`'s freeze entirely — if
the glitch is still visible from those specific controls (as opposed to the in-app scrubber or
natural transitions, both now covered), that's a separate, not-yet-investigated gap.

### 0.5 — FIXED: mini-player swipe-dismiss stuck animation

Overlay mini-player "stays stuck at the bottom for a second" when swiped down — confirmed by the
owner to be specifically the down-swipe: up (expand) was always smooth, only collapse stuck, right
at the end of an otherwise-smooth slide, for about a second before the bar actually disappeared.

**Root cause, confirmed by reading `NowPlayingOverlay.kt`'s `settleTo` and `Motion.kt` together.**
The collapse slide (`dragPx`/`settle: Animatable<Float, _>` animating from `0f` to `collapseOffset`,
roughly 2000px on this device) used `Motion.spatial()` — `spring(dampingRatio = 0.8f,
stiffness = 380f)` with no explicit `visibilityThreshold`. `screenSlide()`, the sibling spec three
lines below it in the same file, already exists *because* the generic default threshold (tuned for
a 0f..1f alpha/scale range) is wrong at pixel scale — its own doc comment says so. `settleTo`
never got the same treatment. Against a ~2000px distance, the spring kept correcting sub-pixel
error well after the slide was visually indistinguishable from finished, and — critically —
`onCollapse()` (the call that actually swaps the overlay for the compact `MiniPlayerBar`,
`NowPlayingOverlay.kt:169-172`) only fires *after* `settle.animateTo(...)` returns, which doesn't
happen until the spring is within its threshold of the target. The visible "stuck" second was that
gap between looking arrived and the coroutine agreeing it had arrived.

**Fix, shipped in PR #54 — real, but not enough.** Added `Motion.spatialOffsetPx()`: the same
spring with an explicit 1px `visibilityThreshold`, mirroring why `screenSlide()` needed one.

**Still reproducing after it shipped, and the arithmetic says why.** The spring is `ζ = 0.8,
k = 380`, so `ω = √380 ≈ 19.5 rad/s` and the error decays as `e^(-15.6t)`. From a ~2000px travel,
the generic 0.01px default needed `ln(200000)/15.6 ≈ 0.78s`; the 1px threshold cut that to
`ln(2000)/15.6 ≈ 0.49s`. So the fix removed ~300ms of a tail that still had ~490ms in it — a real
improvement that lands nowhere near short enough to stop reading as "stuck", which is exactly what
the owner reported next. The threshold was the right lever; it was not the only one.

**Second fix, shipped in PR #55:** a dedicated `Motion.dismissOffsetPx()` for the collapse alone,
changing all three terms of the settling time rather than one — critically damped (a dismissal
that bounces back toward the viewer is wrong on its own terms, and the oscillation is what the
tail is spent converging out of), `k = 1200`, and a 4px threshold, which against a travel three
orders of magnitude larger is below anything visible. `(1 + ωt)e^(-ωt) = 4/2000` lands near
**240ms**. `spatialOffsetPx` stays as-is for the expand and the return-to-rest, where a surface
is *arriving* and the overshoot is deliberate.

**Why the asymmetry the owner noticed is real and not perceptual:** the collapse is the only
settle with something waiting on it. `onCollapse()` — the call that swaps the overlay for the mini
bar — cannot fire until `animateTo` returns, because releasing earlier lets the parent drop the
composable mid-slide (`NowPlayingOverlay.kt`'s own comment records that). The expand has no such
gate: it animates into place and nothing happens afterwards. So the spring tail is invisible going
up and fully visible coming down.

**Still worth checking on-device:** the settle starts from rest via `settle.snapTo(dragPx)` and is
handed no initial velocity, because `detectVerticalDragGestures.onDragEnd` supplies none. A fast
flick therefore decelerates to a stop and then re-accelerates under the spring, which is its own
small disconnect. Fixing it needs a `VelocityTracker` on the drag and `animateTo(initialVelocity =
…)`; not done here, and only worth doing if 240ms still doesn't feel right in the hand.

**Critical files:** `ui/design/Motion.kt` (`spatialOffsetPx`), `ui/screens/NowPlayingOverlay.kt`
(`settleTo`'s default `spec` parameter).

### 0.7 — NEW FINDING: a wedged process survives a plain app-close, and the next launch inherits it

Not in the original report — surfaced while investigating 0.1/0.2 live: after the 58-minute
retry-storm session (0.2), simply closing and reopening the app did **not** get a fresh process.
`adb shell ps` showed the *same* PID from the retry-storm session, `lastStateTime` nearly 9 hours
stale, still alive and still logging the identical `SendspinExoEngine` spam — and the app was
observed stuck on the splash ("mushroom") screen, never proceeding to the main UI. No ANR trace
was recorded (`/data/anr/` empty), so this isn't a formal "Application Not Responding" freeze —
more likely a logical hang, e.g. a splash/loading screen awaiting a state that a process already
wedged by 0.2's busy-loop never emits.

**A `Force stop` from Android Settings (not just closing the app) was required to actually kill
the process** — confirmed via `ActivityManager: Killing 19646:com.engabd.sendpin/u0a615`,
followed by a genuinely fresh `Start proc 12538:...` on relaunch, which did proceed past the
splash screen normally.

**Assessment:** this is very likely a *downstream consequence* of 0.2 (a process that spent 58
minutes in a tight busy-loop, holding whatever locks/state that loop touched, is a reasonable
candidate for ending up wedged) rather than an independent bug — and 0.2's fix (bounding the
retry) should prevent the wedging from happening in the first place. Not separately fixed here;
flagged so it isn't mistaken for a new, unrelated splash-screen bug if seen again. **Follow-up
if it recurs post-0.2-fix:** find what the splash screen actually awaits before navigating past
itself, and whether that condition can be satisfied even from a long-lived, previously-stressed
process — a normal app close/reopen should never require a manual Force Stop to recover.

## Phase 3 — Premium visual push

**Sequencing:** color pipeline first since later work consumes it; a reduced-motion primitive
before shipping new animated surfaces; the rest is largely parallelizable.

1. **Colour accuracy first; wide gamut after.** Reordered on the owner's judgement, and the
   judgement was right: the palette felt "limited", accurate for green covers and off for the
   rest. That is not a gamut problem — a wider gamut would have rendered the same wrong colours
   over a larger volume.
   - **DONE, in PR #55: the lift moved from HSL to OKLCh.** The extraction was never the weak
     part; the *lift* — turning an extracted colour into one the app paints with — was. It ran in
     HSL, whose lightness is not perceptual, and it clamped the result into `S ∈ 0.50..0.72`,
     `L ∈ 0.58..0.70`. Two consequences, both matching the report exactly. **Hue favouritism:** at
     `L = 0.64, S = 0.6` a green lands at relative luminance 0.55 and a blue at 0.19 — the same
     number on the dial, nearly three times the light, which is precisely why green covers looked
     right and others looked muddy. **Flattening:** with two of three dimensions clamped that
     hard, only the hue survived from the artwork, so a muted watercolour sleeve and a neon one
     arrived at nearly the same intensity.
   - Now: hue kept exactly, chroma is the cover's own (floored as a *fraction of what sRGB can
     hold at that lightness and hue*, since the gamut is far wider in yellow than in blue, and
     never capped below the gamut boundary), lightness a fixed perceptual target so no hue is
     quietly favoured. Out-of-gamut results give up chroma by bisection at constant L and h
     rather than clipping RGB, which shifts hue — saturated blue drifts violet, deep red drifts
     orange.
   - Side effect worth having: the lift is pure Kotlin now, so it dropped this file's last
     `androidx.core.graphics` call. `AlbumPaletteTest` used to say the lift "is not covered here";
     it is covered now, by six tests including one that pins equal perceived lightness across six
     hues — which is the test the old implementation would have failed.
   - **Still open — wide gamut (Display P3).** Now a genuine enhancement rather than a fix, and
     bigger than the plan implied: `Bitmap.getPixels()` returns sRGB regardless of the bitmap's
     colour space, so `paletteOf` cannot see wide-gamut values at all today. It needs a changed
     decode (Coil 2.7 offers `bitmapConfig(RGBA_F16)` but no colour-space setter), a P3-aware
     `rgbToOklab`, and `Window.setColorMode(COLOR_MODE_WIDE_COLOR_GAMUT)`. Judgeable only on a
     P3-capable display.
2. ~~**Reduced-motion accessibility.** A global multiplier/kill-switch in `design/Motion.kt:32-67`,
   sourced from the system "remove animations" setting, before items 3-5 so they inherit it.~~
   **DONE, and the premise was wrong — a multiplier would have been redundant.** Verified
   against the Compose sources actually on the classpath (UI/animation-core 1.11.4), not
   assumed: `WindowRecomposer` already installs a `MotionDurationScale` reading
   `Settings.Global.ANIMATOR_DURATION_SCALE` and watching it via a `ContentObserver`, and
   `animation-core` already consumes it everywhere the app animates. Finite animations "end
   in the next frame callback" at a scale of 0, so every spec in `Motion` is *already*
   instant with no help from us; adding a second multiplier would only have fought the one
   that exists.
   - **The real gap is `InfiniteTransition`, which behaves differently:** it *suspends* on
     `snapshotFlow { durationScale }.first { it > 0f }` rather than ending. An infinite
     animation has no end to jump to, so "animations off" leaves it **frozen wherever it
     happened to be** — a refresh icon stopped at 200°, and later a shimmer stuck mid-sweep.
     Frozen mid-gesture reads as a broken screen, and no duration scale can fix it, because
     a still frame of an animation is not a design.
   - **Shipped instead:** `LocalReducedMotion` + `rememberReducedMotion()` in `design/Motion.kt`,
     provided by `SendspinTheme`, reading `ValueAnimator.areAnimatorsEnabled()` and re-read on
     `ON_RESUME` (the same pattern as `rememberIsIgnoringBatteryOptimizations`, for the same
     reason: changing the setting means leaving the app). It answers a *design* question —
     given that motion is off, what should this surface be instead? — rather than a timing
     one. Applied to both existing `rememberInfiniteTransition` refresh spinners
     (`LibraryScreen`, `SpeakersScreen`), which froze crooked before.
   - **Items 3-5 must consult it**, and this is why item 5 in particular needs it: a shimmer
     is an infinite transition, so without an explicit opt-out it freezes as a gradient
     stuck part-way across a tile instead of resolving to a flat placeholder.
3. **Real glass panels.** Extend the `Modifier.blur` infrastructure already proven in
   `MeltBackdrop`/`CastGlow` (`SendspinDesign.kt:116-157`) to the flat-alpha-faked `GlassCard`,
   `Pill`, `IconChip`, etc. (`SendspinDesign.kt:233-248`).
4. **Shared-element flight into Now Playing.** Extend `sharedArt`/`SharedTransitionLayout`
   (`ui/design/SharedTransition.kt:42-51`, already proven grid→`AlbumDetailScreen`) so tapping a
   track flies its art into Now Playing too.
5. **List loading shimmer** for `LibraryScreen.kt` grid tiles (currently flat placeholder boxes).
6. **Custom predictive-back gesture**, replacing the ~20+ plain `BackHandler` sites with
   `PredictiveBackHandler`. Largest-surface item — do last, as a mechanical sweep.

**Housekeeping:** ~~remove the dead `androidx.palette:palette-ktx` dependency
(`app/build.gradle.kts:152`) — zero imports, superseded by the custom extractor.~~ **Done** —
re-confirmed zero imports across the source tree before removing it.

**Critical files:** `ui/design/AlbumPalette.kt`, `ui/theme/Color.kt`, `ui/theme/Theme.kt`,
