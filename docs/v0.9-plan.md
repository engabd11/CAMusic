# v0.9 plan — emergency stabilization, then the premium roadmap

## Context

CAMusic (package `com.engabd.sendpin`) is a mature app (v0.8.8, ~141 Kotlin source files, 526 JVM
unit tests) with three roles: a Sendspin protocol player that registers with Music Assistant for
remote-controlled/grouped multi-room playback, a standalone library client (Navidrome/Subsonic/
Jellyfin/local files) with downloads, and a Philips Hue light-sync engine (through Home Assistant's
syncoV2, or direct-to-bridge). The ambition has grown past the original "sendspin player" scope:
the best audiophile Android player, a browsing experience as rich and premium as the album art and
OLED/HDR displays it runs on, and a direct Hue light sync that beats Spotify's.

This plan started as a forward-looking roadmap, built by reading every internal planning doc and
then verifying every load-bearing claim directly against source (the docs drift from the code in
both directions — some things marked "done" aren't reachable by real users, some marked "untouched"
already shipped). **While that roadmap was being finalized, the owner reported the app is currently
broken in several concrete, reproducible ways on v0.8.8, and connected a physical device (Samsung
Galaxy S23) so this could be diagnosed with real crash logs and live logcat instead of guesswork.**
That changed the priority order completely: a roadmap toward "world-class premium" is moot while
the app's core function — playing Music Assistant audio at all — doesn't work. **Phase 0 below is
therefore new, and every item in it is either a confirmed root cause (code + live device log, not
speculation) or an explicitly flagged hypothesis awaiting confirmation.** The rest of the plan
(Phases 1-5) is the original roadmap, renumbered to follow stabilization.

Three scoping decisions that shape Phases 1-5:
- Testing happens on a real device after cutting a release, not before — Phase 1 produces a
  concrete on-device checklist for that workflow.
- Verifying and promoting the new ExoPlayer+Oboe MA-playback engine to default is a near-term
  priority (also the reachability unlock for direct Hue sync on MA playback) — now gated on Phase
  0 actually fixing that engine first, since it's one of the two confirmed-broken paths.
- The HDR/OLED visual push starts with wide-gamut (Display P3) accent colors, not a full HDR
  gainmap pipeline.

## Phase 0 — Emergency stabilization (fix confirmed-broken playback, do this first)

Reported by the owner, all reproducing on v0.8.8 right now: MA playback doesn't work regardless of
the experimental-engine setting; phone volume changes reach the player but glitch back toward
100%, and in-app volume changes don't reach the phone; selecting Jellyfin and playing a song
crashes the app and it won't reopen until cache is cleared; the mini-player sticks for a second
when swiped down; and the MA timeline briefly jumps then snaps back on track start and on every
seek (Navidrome doesn't have this). Diagnosed against a connected device: `adb logcat -d -b crash`
and the main log buffer, cross-referenced with the exact source lines.

### 0.1 — CONFIRMED: two services collide on the same MediaSession ID and crash the process

**Root cause, proven by direct code read + device crash log, not a guess.**
`SendspinService.kt:464` and `LocalPlaybackService.kt:86` each build a media3 session the same way:

```kotlin
mediaSession = MediaSession.Builder(this, player).build()   // no .setId(...)
```

Neither call sets `.setId(...)`, so both default to the same empty-string session ID. Media3
enforces that session IDs be unique **per process** — the second `MediaSession` constructed with a
colliding ID throws. The device's crash buffer shows exactly this, repeatedly, for both services:

```
IllegalStateException: Session ID must be unique. ID=
  at SendspinService.onCreate(...:59)          <- and separately, at other times:
  at LocalPlaybackService.onCreate(...:51)
```

Eleven crash-and-restart cycles were captured in under four minutes on-device (05:30:21-05:34:09),
alternating between the two services, each `RuntimeException: Unable to create service` killing
the whole process. This is almost certainly new since the media3-session migration (`0927786`) —
that commit is what gave `SendspinService` its own `MediaSession` for the first time;
`LocalPlaybackService`'s session predates it and presumably worked fine in isolation, but the two
now collide whenever both are constructed in the same process.

**Why this explains multiple symptoms at once:**
- **"Can't play on MA regardless of experimental setting"** — if `LocalPlaybackService`'s session
  already exists (e.g. from a prior local-playback attempt, or app state that keeps it alive) and
  the user then starts MA playback, `SendspinService.onCreate()` throws immediately — before any
  engine-specific code (old or new) ever runs. The failure is upstream of engine selection, so of
  course toggling the experimental setting doesn't change the outcome.
- **The Jellyfin crash that requires a cache clear** — `LocalPlaybackService` is the same service
  Jellyfin, Navidrome, and local-file playback all share. It crashed with the identical exception
  in the captured buffer. This is very likely not Jellyfin-specific at all — any local-playback
  start while a colliding session exists would trigger it. The "won't reopen until cache is
  cleared" symptom fits a process that keeps recreating both services on launch (e.g. an
  auto-reconnect/restore-state path) and hitting the same collision every time, until whatever
  state drives that recreation is cleared.

**Fix:** give each `MediaSession.Builder` a distinct, stable `.setId(...)` (e.g. `"sendspin"` and
`"local"`). Small, low-risk, well-understood media3 requirement. **Do this first** — it likely
single-handedly resolves two of the six reported symptoms.

**Critical files:** `service/SendspinService.kt:464`, `service/LocalPlaybackService.kt:86`.

### 0.2 — CONFIRMED: unbounded retry storm in the experimental engine

**Root cause, proven by code read + 58 minutes of live device log, not a guess.**
`SendspinExoEngine.kt:129-134`:

```kotlin
private val playerListener = object : Player.Listener {
    override fun onPlayerError(error: PlaybackException) {
        Log.e("SendspinExoEngine", "player error: ${error.errorCodeName}", error)
        player.prepare()
    }
}
```

The code's own comment acknowledges the risk: retrying via `prepare()` is "enough as long as
whatever caused the error doesn't recur." On-device, it recurred — immediately, every time, for
the entire test session. The device log shows **311,760 repetitions** of:

```
E SendspinExoEngine: player error: ERROR_CODE_TIMEOUT
Caused by: Player stuck buffering with no progress for 600000 ms
```

firing roughly every 150-200ms, continuously, from 11:30:04 to at least 12:28:36 — **58 straight
minutes**, only stopping when the capture ended. This is a genuine busy-loop: `onPlayerError` →
`player.prepare()` → same stuck `SendspinDataSource` → same error → repeat, with no retry limit,
no backoff, and nothing resetting the underlying data source between attempts. The device log also
shows sustained GC pressure and repeated "long monitor contention... for 100-180ms" warnings on
the main thread throughout the window — this isn't just a silent log spam, it's actively costing
CPU, battery, and thermal headroom the entire time, while producing no audio and no user-visible
error state.

**A separate, open question this surfaces:** during that entire 58-minute window, the
`SendspinClient` protocol log shows only the periodic `rx server/time` heartbeat — no
`server/hello`, no `stream/start`, no `server/state` at all (confirmed by checking what
`SendspinClient` actually logs: everything except `server/time` goes through a log call that
would have appeared). The WebSocket connection to MA itself was healthy the whole time. That means
MA never actually dispatched a stream to this player during the whole test — which is either a
separate server-side/registration issue, or the play request never correctly reached MA in the
first place. **This needs a fresh, deliberately-logged repro** (reproduce with logcat capturing
from the moment "play" is pressed, not mid-session) to see whether `stream/start` ever arrives at
all — that's the deeper question behind why the engine had nothing to play in the first place.

**Fix, two parts:**
1. **Immediate:** bound the retry in `onPlayerError` — a small retry count with backoff, and once
   exhausted, surface a real failure state (stop, show an error, don't spin forever). This alone
   turns a battery-draining infinite loop into a bounded, user-visible failure, regardless of the
   deeper cause.
2. **Root cause:** with 0.1 fixed (so `SendspinService` can even stay alive), reproduce again with
   full logging from the moment playback starts, to determine whether `stream/start` is being
   requested/sent/received at all, and if not, why not — check the play-initiation path in
   `service/Playback.kt` for what actually triggers `SendspinExoEngine.play(...)`/`prepare()`, and
   whether it fires before or independent of confirmation that MA will actually stream.

**Critical files:** `audio/SendspinExoEngine.kt:129-134`, `audio/SendspinDataSource.kt`,
`protocol/SendspinClient.kt`, `service/Playback.kt`.

### 0.3 — HYPOTHESIS (not yet confirmed): bidirectional volume sync glitch

Phone volume changes reach the player but "glitch, trying to go back to 100%"; in-app volume
changes don't reach the phone. Direct code read of `SendspinService.kt`'s `ShadePlayer` shows the
mechanics involved, but the device log buffer had already rotated past whatever happened during
the actual repro by the time it was captured, so this is a code-grounded hypothesis, not a
confirmed root cause:

- When this phone **is** the MA player (`isSelf`), published volume comes straight from
  `deviceVolumePercent()` — the phone's own OS volume (`SendspinService.kt:185,203-204`).
- When a **remote** speaker is active, published volume comes from `remote.volumeLevel`, which is
  MA's own reported figure for that speaker, refreshed via `ma.now` (`SendspinService.kt:165,185`).
- `setVolumePercent()` (`:405-409`) writes to both the phone's own volume **and** calls
  `ma.setVolume(...)` — a plausible feedback path: phone volume change → app tells MA → MA's
  acknowledgement/broadcast comes back through `ma.now`/`server/command` → app re-applies it. If
  that round-trip ever carries a stale or default figure (e.g. before the real value has
  propagated server-side), the visible symptom would be exactly "briefly jumps toward 100% before
  settling."

**Next step:** reproduce with the device connected and logcat capturing from the moment the volume
is changed, filtering for `ShadePlayer`/`SendspinService`/`Playback` volume-related log lines (add
temporary logging around `setVolumePercent`, `handleSetDeviceVolume`, and wherever incoming
`server/command` volume updates are applied, if they aren't already logged) to see the actual
sequence of values.

**Critical files:** `service/SendspinService.kt:158-203,372-409`, `service/Playback.kt` (MA volume
command handling).

### 0.4 — Needs investigation: MA-only timeline/seek glitch (long-standing)

On track start, the position briefly shows ~1 second then snaps to 0; on seek, it overshoots by
~2 seconds then snaps to the target. Navidrome (ExoPlayer-driven, no separate estimation layer)
does not show this. Not a new regression — described as long-standing. Likely candidates based on
architecture (not yet confirmed against logs): `ui/viewmodel/PlayerPositionTracker.kt`,
`protocol/ProgressProjection.kt` — the MA path has an extra position-estimation layer between
server updates that the direct ExoPlayer/Navidrome path doesn't need, and an optimistic local
estimate briefly racing against the real server-reported position on start/seek would produce
exactly this symptom. Lower urgency than 0.1/0.2 (cosmetic, tolerated "for a long time"), but
still undermines the premium/smooth goal directly — schedule right after the crash/retry-storm
fixes, with its own targeted device repro.

### 0.5 — Needs investigation: mini-player swipe-dismiss stuck animation

Overlay mini-player "stays stuck at the bottom for a second" when swiped down. The drag-to-dismiss
gesture is relatively new (v0.8.8: "the bar can be dragged as well as tapped"), so this is a
plausible fresh regression in that gesture/animation code, likely in `NowPlayingOverlay.kt` or a
dedicated mini-player composable, using the spring specs in `design/Motion.kt`. Not yet
root-caused — lowest severity of the six (cosmetic), schedule after 0.1-0.4.

### 0.6 — Settings reorganization: per-server settings live under each server

**Explicit request:** audio settings for each player need to be under each relevant server — Music
Assistant related info or experimental settings should live inside the Music Assistant server's
settings page, and so on. This extends a pattern the app already applies successfully elsewhere —
MA's gapless/crossfade config already lives on the MA server's own settings card
(`PlayerSettings.kt:220-249`, confirmed shipped). The experimental engine toggles
(`useExoPlayerForSendspin`, `useOboeOutput`) currently sit in a generic `AudioSettings.kt:277-318`
section instead of under the Music Assistant server's own settings — move them there, and audit
the rest of `AudioSettings.kt` for any other setting that's really specific to one backend
(Navidrome/Jellyfin/MA) and relocate it under that server's own settings page the same way. Bundle
this with Phase 2 below (engine promotion), since it touches the exact same settings card.

**Critical files:** `ui/screens/settings/AudioSettings.kt`, `ui/screens/settings/PlayerSettings.kt`
(or wherever the per-server settings cards live), `ui/screens/SettingsScreen.kt`.

## The big surprises from the original roadmap research (context for Phases 1-5)

1. **The unconditional media3-session migration risk was real** — and 0.1 above is likely a direct
   consequence of it. `SendspinService` replacing `MediaSessionCompat` with a real media3
   `MediaSession` (commit `0927786`) is careful, well-commented work — direct reads of
   `SendspinService.kt:302-364` show deliberate handling of skip-previous-vs-restart semantics and
   local-vs-remote device volume routing — but its own commit message admitted it was "NOT yet
   verified on device," and the session-ID collision is exactly the kind of thing on-device
   verification would have caught immediately.
2. **The v0.8.8 headline feature is dormant for real users even once 0.2 is fixed.** "Direct Hue
   sync now works for MA playback" is only true when `AppSettings.useExoPlayerForSendspin` is on —
   defaulting to `false`, under a settings card explicitly labeled "Experimental / Not ready for
   everyday use." The Hue tap-switching plumbing itself is already fully wired
   (`SendpinApp.kt:88-109`, `DirectLightSync.kt:235-242`) — promoting the engine (Phase 2) is what
   makes it reachable, once it actually works (Phase 0).
3. **The visual foundation is stronger than the docs suggest.** Real role-based theming with true
   OLED black as a distinct variant from charcoal "Dark" (`Color.kt:47-75`), Material You already
   wired in scoped correctly (`Theme.kt:187-200`), a genuinely sophisticated from-scratch CIELAB
   k-means album-palette extractor with population-weighted multi-swatch output
   (`AlbumPalette.kt`), and real GPU blur already powering the Now Playing backdrop
   (`SendspinDesign.kt:116-157`). But there is zero HDR/wide-gamut handling anywhere, the "glass"
   panels used everywhere else are a flat-alpha fake next to that same real blur infrastructure,
   there's no reduced-motion accessibility support, and album art doesn't fly into Now Playing.
4. **The Hue light-sync engine itself doesn't need more musical intelligence to beat Spotify.**
   Tempo PLL, beat-grid locking, song-structure detection, scheduled wavefronts, pre-analyzed
   track maps, a spatial field across the room with a sustain layer for held notes — all shipped,
   all unit-tested (~5,400 lines under `hue/`/`audio/`). Spotify has no native Hue Entertainment
   API integration at all. The gap is reachability and verification, not algorithmic sophistication.
5. **Technical debt is concentrated exactly where the two headline goals live, and is growing.**
   `ma/LibraryViewModel.kt` (browsing) is **2,411 lines**, `hue/SyncoEngine.kt` (light sync) is
   **2,079 lines**, `ui/screens/LibraryScreen.kt` is **1,448 lines** — all larger than the last
   audit recorded, confirming they grow every release. These are precisely the files Phase 3/4
   feature work below needs to touch.

## Phase 1 — Verify and harden the background/notification path

Once Phase 0 makes playback actually work, this becomes testable. This blocks confidently shipping
anything else, since every later phase either runs inside these services or depends on the
connection they keep alive.

**Code changes:**
- `OnboardingWizard.kt:553,589-601` — `batteryVisited` only records that the exemption *settings
  screen was opened*, never that the exemption was *granted*. Add a `LifecycleEventObserver` on
  `ON_RESUME` that calls `PowerManager.isIgnoringBatteryOptimizations(packageName)` and drives the
  onboarding step's "done" state from that ground truth instead.
- Add a persistent warning surface (near `AudioSettings.kt`'s diagnostics, or a Settings banner)
  that fires whenever the exemption is not currently granted — OEM Doze management can revoke it
  later even after onboarding succeeded once.
- Leave `SendspinConnectionService.onTaskRemoved` (`:315-319`) as the deliberate no-op it is.

**On-device checklist, targeting the `ShadePlayer` migration:**
- Lock screen during MA playback: play/pause/next/prev/seek, volume rocker, artwork. Confirm
  skip-previous always goes to the previous track and never restarts the current one
  (`SendspinService.kt:340-348` deliberately overrides media3's default threshold).
- Bluetooth headset/speaker hardware buttons + AVRCP metadata.
- Select a **remote** MA speaker as target: confirm lock screen/Bluetooth shows "Playing on
  &lt;speaker&gt;" and transport/volume route there, not to the phone (`DeviceInfo.PLAYBACK_TYPE_REMOTE`
  vs `LOCAL`, `SendspinService.kt:354-364`).
- Swipe the app from Recents → confirm the connection notification persists and stays connected.
- With the app backgrounded and then fully killed, trigger an HA→MA TTS announcement from another
  device → confirm it plays and regular playback resumes correctly afterward.
- `adb shell dumpsys deviceidle force-idle` → confirm the WebSocket survives Doze.
- On an aggressive-OEM device (Samsung included — called out in `OnboardingWizard.kt` as a known
  risk): screen off 10+ minutes, confirm still connected.

**Critical files:** `service/SendspinService.kt`, `service/SendspinConnectionService.kt`,
`ui/screens/OnboardingWizard.kt`, `AndroidManifest.xml`.

## Phase 2 — Verify and promote the new engine to default, finish settings reorg

**Sequencing:** with 0.2 fixed, `SendspinExoEngine` should actually work. Run Phase 1's checklist
on the **default (old) engine first**, then repeat with `useExoPlayerForSendspin=true` (Oboe still
off) as its own pass, then Oboe on as a third pass — one axis at a time.

**Steps:**
1. A/B audio correctness across FLAC/Opus/PCM and multi-room clock-sync drift between the two
   engines.
2. Promote `useExoPlayerForSendspin` to default **on its own** first. `bitPerfect24Bit` + native
   Oboe output together is a confirmed, explicitly unhandled gap (`SendspinExoEngine.kt:34-42`),
   and Oboe's native path has not been run on real hardware at all — keep `useOboeOutput` opt-in
   for a later round.
3. Verify the Hue tap-switch end-to-end (switch between local and MA playback mid-session, confirm
   lights follow without glitching) — the wiring already exists, this is verification only.
4. Complete the settings reorg from 0.6: move the (by-then-proven) engine toggle under the Music
   Assistant server's own settings page, update its copy once it's no longer "Experimental."
5. Keep `SendspinAudioEngine` in the codebase as a fallback for at least one release after
   promotion.

**Critical files:** `data/AppSettings.kt:484-499`, `service/Playback.kt:370-389`,
`audio/SendspinExoEngine.kt`, `SendpinApp.kt:74-126`, `ui/screens/settings/AudioSettings.kt:277-318`.

## Phase 3 — Premium visual push

**Sequencing:** color pipeline first since later work consumes it; a reduced-motion primitive
before shipping new animated surfaces; the rest is largely parallelizable.

1. **Wide-gamut (Display P3) color pipeline.** Replace `AlbumPalette.kt:487`'s
   `.allowHardware(false)` + hardcoded sRGB D65 matrix (`AlbumPalette.kt:90-99`) with wide-gamut-
   aware decoding and `ColorSpace.Named.DISPLAY_P3`-based extraction, plus
   `Window.setColorMode(COLOR_MODE_WIDE_COLOR_GAMUT)` where supported. A natural upgrade to the
   existing CIELAB k-means extractor, not a rewrite.
2. **Reduced-motion accessibility.** A global multiplier/kill-switch in `design/Motion.kt:32-67`,
   sourced from the system "remove animations" setting, before items 3-5 so they inherit it.
3. **Real glass panels.** Extend the `Modifier.blur` infrastructure already proven in
   `MeltBackdrop`/`CastGlow` (`SendspinDesign.kt:116-157`) to the flat-alpha-faked `GlassCard`,
   `Pill`, `IconChip`, etc. (`SendspinDesign.kt:233-248`).
4. **Shared-element flight into Now Playing.** Extend `sharedArt`/`SharedTransitionLayout`
   (`ui/design/SharedTransition.kt:42-51`, already proven grid→`AlbumDetailScreen`) so tapping a
   track flies its art into Now Playing too.
5. **List loading shimmer** for `LibraryScreen.kt` grid tiles (currently flat placeholder boxes).
6. **Custom predictive-back gesture**, replacing the ~20+ plain `BackHandler` sites with
   `PredictiveBackHandler`. Largest-surface item — do last, as a mechanical sweep.

**Housekeeping:** remove the dead `androidx.palette:palette-ktx` dependency
(`app/build.gradle.kts:152`) — zero imports, superseded by the custom extractor.

**Critical files:** `ui/design/AlbumPalette.kt`, `ui/theme/Color.kt`, `ui/theme/Theme.kt`,
`ui/design/SendspinDesign.kt`, `ui/design/SharedTransition.kt`, `ui/design/Motion.kt`,
`ui/screens/LibraryScreen.kt`, `ui/screens/NowPlayingScreen.kt`.

**Deferred/exploratory:** true HDR gainmap album-art decoding — most source covers don't carry
gainmaps yet, narrower device support, do this after the wide-gamut work captures most of the win.

## Phase 4 — Audiophile/browsing feature completion

**MA-path gapless playback.** The confirmed-open item on the primary playback path: `stream/end`
is byte-identical for "paused" and "track boundary," so every MA-path album has an audible gap.
Fix already designed: after `stream/end`, watch for `server/state` with `playback_speed:0`
arriving within a short window → pause/flush; if `stream/start` arrives first → track boundary,
keep the tail. Independent of which engine renders audio, but the payoff is gated on Phase 2
shipping (ExoPlayer supplies real gapless transitions).

**Critical files:** `protocol/SendspinClient.kt`, `service/Playback.kt`.

No other items are added here beyond what's confirmed still-open by direct code verification —
several "smaller polish" items from older docs (multi-disc grouping, MA player config UI, USB DAC
readouts, warm reconnect) turned out to already be shipped. If a broader sweep for smaller open
items is wanted, that's worth a short dedicated verification pass first.

## Phase 5 — Platform & infrastructure

**Refactor `ma/LibraryViewModel.kt` (2,411 lines) and `hue/SyncoEngine.kt` (2,079 lines) as their
own step, before Phase 3/4 touch them further.** These are exactly the files browsing UI and
light-sync work need to edit, they're the largest and riskiest files in the app, and they grow
every release. Scope as incremental, low-risk extraction-by-responsibility, not a redesign.

**Then, independent of each other and of the refactor:**
- **Android Auto** — touches the same notification/session code Phase 0/1 just stabilized, so
  sequence after Phase 1 is fully verified, not concurrently. Not started at all today.
- **Release signing + CI** — small, config-only. Currently debug-keystore-only, documented as
  deliberate in the README (stability of updates), so this is a "if/when Play Store distribution
  matters" item, not urgent.
- **Real crash-reporting backend** — today is local-JSON-only with an optional manual GitHub
  issue. Given Phase 0 was only diagnosable because a device happened to be connected, this
  becomes more valuable: a real backend would have surfaced the session-ID crash automatically on
  day one.
- **Instrumented tests** — `app/src/androidTest` doesn't exist yet. Most valuable after the
  refactor above and after Phase 0/1 stabilize the service layer — the highest-value first
  instrumented tests are exactly what Phase 0 found by hand; automate those once known-passing.
- **Home-screen widget** (Glance) — doesn't exist yet, independent of everything else.

**Critical files:** `ma/LibraryViewModel.kt`, `hue/SyncoEngine.kt`, `ui/screens/LibraryScreen.kt`,
`AndroidManifest.xml`, `app/build.gradle.kts`, `crash/CrashReporter.kt`.

## Verification

- **Phase 0 is device-verified already for 0.1 and 0.2** — the root causes were confirmed against
  live crash logs and a 58-minute reproduction, not just static analysis. After the fixes land,
  re-run with the device still connected: confirm no `IllegalStateException: Session ID must be
  unique` in `adb logcat -d -b crash` after switching between MA and local playback repeatedly, and
  confirm no `SendspinExoEngine` error spam after a deliberately-broken stream (e.g. airplane mode
  mid-play) — it should retry a bounded number of times and then stop, not run forever.
- **0.3-0.5 need a fresh, deliberately-logged repro** on the connected device — capture logcat
  starting *before* reproducing each bug (`adb logcat -c` to clear, then reproduce, then dump),
  since the buffer rotates fast once the retry storm or other chatty logging is running.
- **JVM unit tests remain the safety net for every phase**: `./gradlew :app:testDebugUnitTest`
  (526 tests) and `./gradlew :app:lintDebug`. Add tests alongside each phase's changes.
- **Phase 1's checklist is the acceptance criteria for the background/notification work**, and the
  three-pass A/B (old engine → ExoPlayer-only → ExoPlayer+Oboe) is the acceptance criteria for
  Phase 2.
- **Phase 3** should be judged on a release build only, per the project's own existing convention
  for judging "feel."
