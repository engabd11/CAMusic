## Phase 1 — Correctness & cleanup

### 1.1 Deprecate and remove `SendspinAudioEngine`

**Problem.** `SendspinAudioEngine.kt` (1,035 lines) is never selected —
`Playback.startSendspin` unconditionally creates `SendspinExoEngine` (line 441:
"the only one"). It is kept for `END_LINGER_MS` and `StreamContinuity`, but
those are not referenced by `SendspinExoEngine`.

**Constraint.** Must not break TTS announcements or current playback.
`SendspinExoEngine` handles `stream/end` and `stream/clear` independently.
`SendspinConnectionService` and `MaNowPlaying` do not reference
`SendspinAudioEngine`.

**Steps:**
1. Extract `END_LINGER_MS` to a top-level constant or a shared
   `SendspinConstants.kt` if `SendspinExoEngine` needs it (verify first — it
   may already have its own).
2. Check every import of `SendspinAudioEngine` across the codebase. The only
   reference should be in `Playback.startSendspin`'s commented-out fallback.
3. Delete `SendspinAudioEngine.kt`.
4. Remove the commented-out fallback in `Playback.startSendspin`.
5. Run `./gradlew :app:testDebugUnitTest` — `StreamContinuityTest`,
   `SchedulingTest`, `StreamQualityTest` and `SinkStallDetectorTest` may
   reference it. If they do, update or remove the tests.
6. Verify `SendspinConnectionService` TTS path: TTS arrives as a
   `stream/start` + audio frames, same as music. `SendspinExoEngine` handles
   it. No change needed.

**Files:**
- `audio/SendspinAudioEngine.kt` — delete
- `service/Playback.kt` — remove dead fallback
- Tests referencing `SendspinAudioEngine` — update

**Risk:** Low. The class is dead code. The risk is a test that imports it.

### 1.2 Fix Jellyfin scrobble inaccuracy

**Problem.** `JellyfinSource.scrobble()` computes position as
`System.currentTimeMillis() - startedAtMs`, which drifts during pauses. Jellyfin's
scrobble API expects `PositionTicks` (1/10,000,000 second units).

**Current code** (`library/JellyfinSource.kt:102`):
```kotlin
override suspend fun scrobble(id: String, completed: Boolean, startedAtMs: Long?) {
    val posMs = if (completed) 0L else (System.currentTimeMillis() - (startedAtMs ?: 0))
    client.reportProgress(id, posMs, completed)
}
```

**Fix:**
1. Track the actual playback position from `LocalPlayer` (which already
   tracks position via `PlayerPositionTracker`).
2. Pass the real position to `scrobble()` instead of computing from wall clock.
3. For "now playing" reports (`reportProgress`), use `LocalPlayer.currentPositionMs`.
4. For "stopped" reports (`completed = true`), pass the last known position
   before stop, not 0.

**Files:**
- `library/JellyfinSource.kt` — change `scrobble()` signature to accept
  position from caller
- `ui/viewmodel/NowPlayingViewModel.kt` — pass real position to scrobble
- `jellyfin/JellyfinClient.kt` — verify `reportProgress` converts ms → ticks
  correctly

**Test:** Add a unit test that simulates a 10-second pause mid-track and
verifies the scrobbled position matches the playback position, not wall clock.

### 1.3 Investigate and resolve MA duplicated polling

**Problem.** `MaNowPlaying.kt` (500 lines) and `NowPlayingViewModel.kt` both
poll the same MA WebSocket every 5 seconds, issuing the same `players/all` and
`player_queues/all` commands. This doubles the command load on the server.

**Investigation steps:**
1. Map every `players/all` and `player_queues/all` call site in both files.
2. Determine whether `MaNowPlaying` exists as a process-scoped singleton
   because `NowPlayingViewModel` is lifecycle-scoped (tied to the Activity).
   If so, the solution is to expose `MaNowPlaying`'s state as a shared
   `StateFlow` that `NowPlayingViewModel` collects rather than re-fetching.
3. Check whether `NowPlayingViewModel` issues commands that `MaNowPlaying`
   does not (e.g., `player_queues/get_active_queue` for the queue view).
   Those may need to remain, but the shared state (players list, current
   player, now-playing metadata) should come from `MaNowPlaying`.
4. Measure the actual duplicate commands via a log tag or by counting
   `MaApiClient` request IDs.

**Resolution:**
- If duplicate: `NowPlayingViewModel` collects `MaNowPlaying.players` and
  `MaNowPlaying.now` flows instead of polling. Only queue-specific data
  (active queue items) is fetched separately, and only when the queue
  screen is visible.
- If not duplicate (different data): document why both exist.

**Files:**
- `service/MaNowPlaying.kt`
- `ui/viewmodel/NowPlayingViewModel.kt`
- `ma/MaApiClient.kt` — possibly add a log to count requests

**Risk:** Medium. Changing polling structure could introduce stale-state bugs.
Must verify that `MaNowPlaying`'s 5s poll + 300ms sampled events provide
sufficient responsiveness for the Now Playing screen.

## Phase 2 — Features

### 2.1 Beat-matched crossfade (item #2 from analysis)

**Goal.** Instead of a fixed-duration crossfade between tracks on the
standalone path, align the transition to the beat grid of both tracks.

**Infrastructure that exists:**
- `TempoTracker.kt` — predictive beat grid with PLL
- `StructureTracker.kt` — detects sections, builds, drops
- `TrackScanner.kt` + `TrackScanRepository.kt` — offline pre-scan with beat
  grids cached on disk
- `LocalPlayer.kt` — already has smooth transitions (1–12s fade)

**Design:**
1. When the current track is within `crossfadeDuration` of ending, look up
   the pre-scanned beat grid for the **next** track (from `TrackScanStore`).
2. Find the first downbeat after the start of the next track.
3. Align the crossfade start to the nearest beat boundary of the current
   track's live beat grid (from `TempoTracker`).
4. If either track has no scan or no tempo, fall back to the existing
   fixed-duration smooth transition.
5. Expose a setting: "Beat-matched crossfade" (off by default — it requires
   scans to work, and the first play of an unscanned track falls back).

**Files:**
- `audio/LocalPlayer.kt` — crossfade logic
- `audio/TempoTracker.kt` — expose current beat grid
- `audio/TrackScanStore.kt` — lookup next track's scan
- `data/AppSettings.kt` — new setting
- `ui/screens/settings/PlayerSettings.kt` — toggle

**Note:** The existing smooth transitions are the first half. This is the
second. It does not replace them — it enhances them when scans are available.

### 2.2 USB DAC detection and exclusive routing (item #4)

**Goal.** When a USB DAC is connected, show its capabilities and offer to
match the stream format to what it supports.

**Infrastructure that exists:**
- `AudioOutputs.kt` — already enumerates output devices, has
  `maxSupportedSampleRate()` probe
- `DeviceCapabilities.kt` — already has `Route` detection
- `FormatNegotiator.kt` — already probes device sample rate support

**Design:**
1. Listen for `AudioManager.ACTION_AUDIO_BECOMING_NOISY` and
   `AudioDeviceCallback` for USB audio connect/disconnect.
2. On USB connect: probe `AudioDeviceInfo` for supported sample rates and bit
   depths.
3. Show a notification: "USB DAC connected: Topping D90SE — up to 768kHz/32-bit".
4. If the current stream's sample rate is lower than the DAC's max, offer to
   switch (via `FormatNegotiator` or `sendRequestFormat()` for MA, or by
   re-requesting the original file at a higher rate for Navidrome).
5. Add a settings screen: "Output device" showing the current output route
   and its capabilities.
6. For the Oboe path: implement `SendspinNativeOutput.setPreferredDevice()`
   (currently a no-op) to pin the stream to the USB DAC.

**Files:**
- `audio/AudioOutputs.kt` — extend with USB DAC probing
- `audio/DeviceCapabilities.kt` — expose USB route capabilities
- `audio/FormatNegotiator.kt` — respect USB DAC max rate
- `audio/SendspinNativeOutput.kt` — implement `setPreferredDevice`
- `audio/LocalPlayer.kt` — route to USB DAC when available
- `data/AppSettings.kt` — "prefer USB DAC" toggle
- `ui/screens/settings/AudioSettings.kt` — output device display

### 2.6 Settings export/import (item #15)

**Goal.** Export all server configs, credentials, and preferences to an
encrypted JSON file that can be imported on a new device.

**Design:**
1. "Export settings" in Settings → reads all `AppSettings` keys + server list,
   serialises to JSON, encrypts with a user-provided password (using
   `Crypto.kt`'s AES-256-GCM, but with a user password as key instead of
   Keystore — since the Keystore is device-specific).
2. Save to a file via `ACTION_CREATE_DOCUMENT`.
3. "Import settings" reads via `ACTION_OPEN_DOCUMENT`, decrypts, writes to
   `AppSettings`. Prompts before overwriting existing servers.
4. Credentials are re-encrypted with the new device's Keystore on import.

**Files:**
- `data/AppSettings.kt` — export/import methods
- `data/Crypto.kt` — password-based encrypt/decrypt (alongside Keystore)
- `ui/screens/SettingsScreen.kt` — export/import buttons
- `ui/screens/settings/SettingsComponents.kt` — dialog for password

## Phase 3 — Driving mode enhancement

### 3.1 Speed limit audible alert

**Goal.** Optionally beep when the phone's GPS speed exceeds a user-set limit.

**Design:**
1. Request `ACCESS_FINE_LOCATION` (only when speed alert is enabled — runtime
   permission, requested in driving settings, not in the manifest by default).
2. Use `LocationManager.requestLocationUpdates` with `GPS_PROVIDER` only
   while driving mode is active. Minimal interval (5s) to avoid battery drain.
3. Extract `location.speed` (m/s) → km/h.
4. If speed > user-set limit for >5 consecutive readings (to avoid transient
   spikes from GPS noise), play a short beep via `AudioTrack` or
   `ToneGenerator` (not ExoPlayer — needs to overlay current playback).
5. Beep frequency: one short tone per violation, not continuous. Repeat every
   30 seconds while over the limit, not every reading.
6. Setting: "Speed limit alert" toggle + km/h input (default: off, no limit).

**Files:**
- `service/DrivingMode.kt` — add speed monitoring
- `service/DrivingOverlayService.kt` — or a new `SpeedMonitorService`
- `ui/screens/settings/DrivingSettings.kt` — toggle + speed input
- `data/AppSettings.kt` — `drivingSpeedLimitKmh` setting
- `AndroidManifest.xml` — add `ACCESS_FINE_LOCATION` (with `maxSdkVersion`
  removed, but only requested at runtime when feature is enabled)

**Safety considerations:**
- The beep must be subtle, not alarming. A gentle tone, not a harsh alarm.
- Do not show the speed on screen — reading a number while driving is worse
  than hearing a tone.
- The feature is opt-in and off by default.

### 3.2 Auto-pause on phone call

**Goal.** Automatically pause playback when a phone call starts (not just
headphone disconnection, which `ACTION_AUDIO_BECOMING_NOISY` already handles).

**Design:**
1. Listen for `TelephonyManager.CALL_STATE_RINGING` and
   `CALL_STATE_OFFHOOK` via a `PhoneStateListener` (or the modern
   `TelephonyCallback` on API 31+).
2. On `RINGING`: pause playback (via `PlaybackOwner`).
3. On `IDLE` after `OFFHOOK`: do NOT auto-resume — the user may have been in
   a conversation and auto-resume is surprising. Show a notification: "Music
   paused for call — tap to resume."
4. Only active when driving mode is on (or as a general setting: "Pause for
   calls" — off by default).

**Files:**
- `service/DrivingMode.kt` or a new `CallPauseObserver` in `service/`
- `service/PlaybackOwner.kt` — pause/resume routing
- `data/AppSettings.kt` — `pauseForCalls` setting
- `AndroidManifest.xml` — add `READ_PHONE_STATE` (runtime, only when
  feature enabled)

### 3.4 Speed-adaptive volume

**Goal.** Gradually increase volume at higher speeds to compensate for road
noise, without the user touching the volume.

**Design:**
1. Use the same GPS speed readings from §3.1.
2. Map speed ranges to volume offsets:
   - 0–40 km/h: +0 dB
   - 40–80 km/h: +2 dB
   - 80–120 km/h: +4 dB
   - >120 km/h: +6 dB
3. Apply as a gain factor on top of the user's set volume (not replacing it).
4. Smooth ramping (1-second linear fade) to avoid sudden jumps.
5. Setting: "Speed-adaptive volume" (off by default).

**Files:**
- `service/DrivingMode.kt` — speed → volume mapping
- `audio/LocalPlayer.kt` — apply gain offset
- `service/Playback.kt` — apply gain offset for MA path
- `data/AppSettings.kt` — `speedAdaptiveVolume` setting
- `ui/screens/settings/DrivingSettings.kt` — toggle
