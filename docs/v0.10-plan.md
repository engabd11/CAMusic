### 1.2 Fix Jellyfin scrobble inaccuracy

**Problem.** `JellyfinSource.scrobble()` computes position as
`System.currentTimeMillis() - startedAtMs`, which drifts during pauses. Jellyfin's
scrobble API expects `PositionTicks` (1/10,000,000 second units).

**Current code** (`library/JellyfinSource.kt:102`):
```kotlin
override suspend fun scrobble(id: String, completed: Boolean, startedAtMs: Long?) {
    val posMs = if (completed) 0L else (System.currentTimeMillis() - (startedAtMs ?: 0))
    client.reportProgress(id, posMs, completed)
}
```

**Fix:**
1. Track the actual playback position from `LocalPlayer` (which already
   tracks position via `PlayerPositionTracker`).
2. Pass the real position to `scrobble()` instead of computing from wall clock.
3. For "now playing" reports (`reportProgress`), use `LocalPlayer.currentPositionMs`.
4. For "stopped" reports (`completed = true`), pass the last known position
   before stop, not 0.

**Files:**
- `library/JellyfinSource.kt` — change `scrobble()` signature to accept
  position from caller
- `ui/viewmodel/NowPlayingViewModel.kt` — pass real position to scrobble
- `jellyfin/JellyfinClient.kt` — verify `reportProgress` converts ms → ticks
  correctly

**Test:** Add a unit test that simulates a 10-second pause mid-track and
verifies the scrobbled position matches the playback position, not wall clock.

## Phase 2 — Features

### 2.1 Beat-matched crossfade (item #2 from analysis)

**Goal.** Instead of a fixed-duration crossfade between tracks on the
standalone path, align the transition to the beat grid of both tracks.

**Infrastructure that exists:**
- `TempoTracker.kt` — predictive beat grid with PLL
- `StructureTracker.kt` — detects sections, builds, drops
- `TrackScanner.kt` + `TrackScanRepository.kt` — offline pre-scan with beat
  grids cached on disk
- `LocalPlayer.kt` — already has smooth transitions (1–12s fade)

**Design:**
1. When the current track is within `crossfadeDuration` of ending, look up
   the pre-scanned beat grid for the **next** track (from `TrackScanStore`).
2. Find the first downbeat after the start of the next track.
3. Align the crossfade start to the nearest beat boundary of the current
   track's live beat grid (from `TempoTracker`).
4. If either track has no scan or no tempo, fall back to the existing
   fixed-duration smooth transition.
5. Expose a setting: "Beat-matched crossfade" (off by default — it requires
   scans to work, and the first play of an unscanned track falls back).

**Files:**
- `audio/LocalPlayer.kt` — crossfade logic
- `audio/TempoTracker.kt` — expose current beat grid
- `audio/TrackScanStore.kt` — lookup next track's scan
- `data/AppSettings.kt` — new setting
- `ui/screens/settings/PlayerSettings.kt` — toggle

**Note:** The existing smooth transitions are the first half. This is the
second. It does not replace them — it enhances them when scans are available.

## Phase 3 — Driving mode enhancement

### 3.1 Speed limit audible alert

**Goal.** Optionally beep when the phone's GPS speed exceeds a user-set limit,
with a configurable tolerance percentage so minor overages don't trigger it.

**Design:**
1. Request `ACCESS_FINE_LOCATION` (only when speed alert is enabled — runtime
   permission, requested in driving settings, not in the manifest by default).
2. Use `LocationManager.requestLocationUpdates` with `GPS_PROVIDER` only
   while driving mode is active. Minimal interval (5s) to avoid battery drain.
3. Extract `location.speed` (m/s) → km/h.
4. Compute the effective threshold: `threshold = limit × (1 + tolerance / 100)`.
   For example, limit = 80 km/h, tolerance = 5% → threshold = 84 km/h.
   The tolerance accounts for speedometer variance and GPS jitter, so the
   user isn't beeped at 81 km/h on an 80 km/h road.
5. The beep condition is **strictly greater than**: `speed > threshold`.
   Since speed readings are integers, a threshold of 84 means the first
   beep happens at 85 km/h, not 84. The display shows the triggering speed,
   not the threshold: "Beeps at 85 km/h and above".
6. If speed > threshold for >5 consecutive readings (to avoid transient
   spikes from GPS noise), play a short beep via `AudioTrack` or
   `ToneGenerator` (not ExoPlayer — needs to overlay current playback).
7. Beep frequency: one short tone per violation, not continuous. Repeat every
   30 seconds while over the threshold, not every reading.
8. Settings:
   - "Speed limit alert" toggle (default: off)
   - "Speed limit (km/h)" input (default: none)
   - "Tolerance (%)" input (default: 5%) — how far over the limit before
     beeping. Display the computed trigger speed live: "Beeps at 85 km/h
     and above" (not the raw threshold of 84).

**Files:**
- `service/DrivingMode.kt` — add speed monitoring + threshold computation
- `service/DrivingOverlayService.kt` — or a new `SpeedMonitorService`
- `ui/screens/settings/DrivingSettings.kt` — toggle + speed input + tolerance input
- `data/AppSettings.kt` — `drivingSpeedLimitKmh` + `drivingSpeedTolerancePct` settings
- `AndroidManifest.xml` — add `ACCESS_FINE_LOCATION` (only requested at
  runtime when feature is enabled)

**Safety considerations:**
- The beep must be subtle, not alarming. A gentle tone, not a harsh alarm.
- Do not show the speed on screen — reading a number while driving is worse
  than hearing a tone.
- The tolerance prevents nagging on roads where the posted limit is close to
  traffic speed. 5% is a sensible default (4 km/h at 80, 6 at 120).
- The feature is opt-in and off by default.

### 3.2 Auto-pause on phone call

**Goal.** Automatically pause playback when a phone call starts (not just

**Goal.** Gradually increase volume at higher speeds to compensate for road

5. Setting: "Speed-adaptive volume" (off by default).

**Files:**

## Phase 4 — Ambient light shows (non-music)

The Hue Entertainment DTLS pipeline (60 Hz, spatial field renderer, room topology
classification, colour palettes, `FrameDelayQueue`, `FieldSafety` limiter) is
audio-agnostic. `SyncoEngine` already has `renderIdle()` and `renderIdleShow()`
which drive the lights from elapsed time alone — no audio input. This phase
extends that foundation into a suite of standalone light-show scenes.

### 4.1 Ambient scenes (calm, continuous)

#### Sunset / Sunrise simulation

The lights slowly cycle from warm amber to deep orange to soft red over a
user-set duration (15/30/60 min). Circadian rhythm lighting — gentle wake-up
or wind-down. Uses the existing spatial field for even room glow and
`FrameDelayQueue` for smoothness. No FFT, no onset detection — just a
time-driven colour ramp.

**Files:**
- `hue/AmbientScene.kt` — new base class for time-driven scenes
- `hue/SyncoPalette.kt` — sunset/sunrise palette gradients

#### Aurora (Northern Lights)

Slow, flowing waves of green, teal, and violet that drift across the room.
Uses the existing `renderIdleShow()` spatial wave renderer — two out-of-phase
sine waves moving through the room — but with an aurora-specific palette and
slower wave speeds. The room topology classification (line/ring/field) already
determines how the sweep renders. No beats, just flowing colour.

**Files:**
- `hue/AmbientScene.kt` — aurora preset
- `hue/SyncoPalette.kt` — aurora palette

#### Fireplace / candle flicker

Each lamp gets an independent slow flicker — warm orange/yellow with
randomised intensity changes. The existing per-lamp attack and spectral pop
logic (from `SyncoEngine`) is driven by a Perlin noise function instead of
audio onsets. The eye-safety limiter (`FieldSafety.kt`) caps brightness.
Cosy ambient mode — the room feels lit by a fire.

**Files:**
- `hue/AmbientScene.kt` — fireplace noise-driven preset
- `hue/FieldSafety.kt` — reuse as-is

#### Colour wash / "mood ring"

The room becomes a single slowly-shifting colour that reflects a mood the
user picks — calm (blue/teal), energetic (orange/red), focused (green),
romantic (pink/purple), or custom. The colour drifts through adjacent hues
on a 30–60 second cycle. Unlike a static Hue scene, the room breathes.

**Files:**
- `hue/AmbientScene.kt` — mood-driven colour cycle
- `hue/SyncoPalette.kt` — mood palettes

### 4.2 Entertainment scenes (dynamic, show-like)

#### Autonomous fireworks show

The existing `FireworksEffect.kt` is triggered by music onsets today. A
standalone mode runs a scripted show: launch bursts at randomised intervals
(2–8 seconds), each burst a different colour from a festive palette (gold,
red, green, blue, white), each burst at a different position in the room
using the spatial field. The user picks a duration (5 min, 10 min, "until
stopped") and a palette theme (New Year, Australia Day, birthday, custom).

The `FrameDelayQueue` already handles the launch-to-burst delay. The
`FireworksEffect` seed parameter allows deterministic or random shows.

**Files:**
- `hue/FireworksEffect.kt` — add autonomous mode (timer-driven launches)
- `hue/AmbientScene.kt` — fireworks scene wrapper

#### Lightning storm

Strobe-like flashes of cool white/blue at randomised intervals, with a
low-brightness rumble wash between strikes. Intensity scales with "storm
severity" (calm → moderate → severe). The `FieldSafety` limiter caps flash
brightness. A randomised inter-strike interval (3–12 seconds) prevents
predictability.

**Files:**
- `hue/AmbientScene.kt` — lightning scene
- `hue/FieldSafety.kt` — reuse flash limiter

#### Party mode (random colour bursts)

Every 1–3 seconds, a random lamp gets a random colour from a vibrant palette
at full brightness, then fades back. The spatial field makes adjacent lamps
share a softened glow. A "speed" slider controls the burst frequency. The
simplest possible disco effect — just a timer and a random colour generator.

**Files:**
- `hue/AmbientScene.kt` — party burst scene

The lights gradually brighten from 0 to a target brightness over 15–30

can schedule this. When combined with music (the existing sleep timer /
alarm infrastructure), the lights come up first, then music starts — a
complete wake-up experience.

**Files:**

`NotificationListenerService` (sensitive permission, but the app already
asks for `SYSTEM_ALERT_WINDOW` for driving mode — same precedent).

**Files:**
- `hue/NotificationFlasher.kt` — new
- `AndroidManifest.xml` — `NotificationListenerService` registration
- `data/AppSettings.kt` — per-app colour mapping

### 4.5 Architecture for the scene system

All scenes share the same rendering contract: produce `Map<Int, Rgb>` at 60
Hz from a time input. The existing `SyncoEngine.render()` and
`renderIdleShow()` both return this type. The scene system is:

```
AmbientScene (interface)
  ├── duration: Duration?
  ├── palette: SyncoPalette
  ├── render(t: Float, dt: Float): Map<Int, Rgb>   // same as SyncoEngine
  └── scenes:
      ├── SunsetScene
      ├── AuroraScene
      ├── FireplaceScene
      ├── MoodRingScene
      ├── FireworksShowScene
      ├── LightningScene
      ├── PartyScene
      ├── SunriseAlarmScene
      ├── HolidayScene
      └── HalloweenScene
```

`DirectLightSync.kt` already owns the DTLS connection and the render loop. A
new mode enum (`AMBIENT`) alongside `MUSIC` / `FIREWORKS` lets the user pick
a scene from the Lights screen. When `AMBIENT` is selected, `DirectLightSync`
calls `scene.render(t, dt)` instead of `engine.render(frame)`.

**Files (shared):**
- `hue/AmbientScene.kt` — interface + all scene implementations
- `hue/SyncoModes.kt` — add `AMBIENT` to `SyncEffect`
- `hue/DirectLightSync.kt` — ambient mode render loop
- `ui/screens/LightSyncScreen.kt` — scene picker
- `data/AppSettings.kt` — selected scene + parameters
