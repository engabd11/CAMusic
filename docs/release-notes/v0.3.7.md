## What's new since v0.3.6

Five reported faults. The playback ones share a theme, and it is the same one v0.3.6
half-fixed: readings were being used without asking when they were true, and audio was
being thrown away while the app made up its mind.

### The track really does start at the beginning now

v0.3.6 fixed the *gate* — `isReadyForPlaybackStart()` instead of `isSynced()`, so the
head of a stream is no longer scheduled against an offset still seconds wide. It did
not fix what the loop did while that gate was closed, which turned out to be the
larger half of the bug.

`runLoop()` polled a frame off the queue **before** asking the gate, then `continue`d
on HOLD. That `continue` discarded the frame. Every frame arriving while the Kalman
filter converged was silently destroyed — and since the server streams several seconds
ahead, by the time the offset landed the head of the queue was already seconds into
the song. If the clock never converged at all, the audio was simply gone. Hence both
symptoms: tracks starting a few seconds in, and no audio for the first few seconds.

The gate now decides *before* touching the queue. Holding means the frames pile up, so
whenever it opens the head of the queue is still the head of the track. Two smaller
corrections fall out of the same reasoning:

- A head frame whose scheduled moment has passed is now **played, not dropped**. The
  spec's "clients should drop late chunks" is about holding sync mid-stream; applying
  it to the head of a stream deletes the start of the song.
- `submit()` no longer drops the *oldest* queued frame under pressure while the gate is
  armed. That frame is the start of the track — the one thing the gate exists to
  protect.

The stall ceiling drops from 4s to 3s: `client/time` runs at 300ms until it has 50
samples, and the gate wants eight good ones, so ~2.4s is the real cold-start cost.
Warm connections — the normal case, since the connection service holds the socket open
whether or not music is playing — pay nothing.

**One trade-off, deliberately taken.** On a cold connect the track now starts correctly
but this phone may sit a beat behind a sync group until the next track. Silence at the
start of every song is the worse failure.

### The seek bar is drawn against the server's clock

`metadata.timestamp` — which the spec defines as "server clock time in microseconds
for when this metadata is valid" — was parsed and never read. So `track_progress` was
rendered as though it described the moment it was parsed. It doesn't; it describes an
instant already in the past by however long the message took to arrive. The bar ran
ahead of the music, and the next message yanked it back.

The spec gives the formula outright:

    calculated_progress = track_progress + (now - timestamp) * playback_speed / 1000000

That is now `ProgressProjection`, a pure function with the timestamp converted through
the same Kalman filter the audio scheduler uses, unit-tested off-device, and clamped to
the track.

`playback_speed` is read as the spec's integer **×1000** rather than a float
multiplier, and — like `track_duration` before it — parsed flexibly. A strict `Int`
throws on the floats Music Assistant sends, and that throw discarded the **entire**
`server/state`: title, artist and progress all lost over one awkward field.

### "It moves a couple of seconds, then goes back to 00:01"

A separate cause, and the reason that symptom happened on *every* track. Position came
from Music Assistant's five-second poll, and a new track was anchored at zero **at
detection time** — after the server had already been playing for however long the poll
took to notice. The bar started late, ran ahead, and the next poll dragged it back.

When this phone is the selected player, the position engine now anchors on the Sendspin
reading instead: pushed on every change, and dated exactly. It is fed *through* the
existing position tracker rather than around it, so the optimistic freeze that makes
seeking and skipping behave still applies.

### The notification's bar snapped back after a seek

`MaNowPlaying.seekTo()` released its own optimistic freeze immediately after issuing
the seek — before the server could possibly have processed it. The next poll reported
the old position and the bar jumped back, which is precisely what the freeze exists to
prevent.

It is now released only on corroboration: a seek when the server's clock lands near the
target, a skip when the server names a different track, with a watchdog so a server
that goes quiet costs a stuck second rather than a stuck bar. A pending skip is tracked
by its own flag, because the outgoing track id is genuinely unknown if nothing has been
polled yet — and "unknown" must not read as "nothing pending".

### Opening the app from a notification while music played

All three services built their tap intent with `TaskStackBuilder`, which stamps
`FLAG_ACTIVITY_CLEAR_TASK` onto the root intent. It exists to synthesise a back stack
for a deep link, which is the opposite of what a media notification wants: every tap
tore the running task down and rebuilt the Activity, every ViewModel under it and the
whole Compose tree — while a foreground media service was streaming.

Now `NEW_TASK or SINGLE_TOP` against a `singleTask` activity, so the running task comes
forward with its state intact. The three services also get one request code each;
sharing a code meant three handles to whichever intent was registered last.

### The announcements notification followed the music

It had been narrating the current track — "Playing here — …", "Playing on …" — making
it a second, worse copy of the media notification that re-rendered on every play/pause.
It now reports only whether the phone is reachable for announcements, which is the one
thing it is for.

### The corner badge said "Subsonic" while Music Assistant played

v0.3.6 replaced a badge that said "MA" unconditionally with one that reads
`streamdetails.provider`. That is a truthful answer to a different question. Music
Assistant streaming a file out of a Subsonic library is Music Assistant playing — the
queue, the transport and the speaker list are all its — and the badge is about which
backend owns playback.

The badge names the backend again. The provider reading moves into the quality card as
a "From …" line, where it is detail about the file rather than a claim about the
player.

### Refreshing the library

Neither backend pushes a "library changed" event, so a newly added album stayed
invisible until the app was restarted. There is a refresh button in the library header
now. It re-pulls what is actually on screen: a search re-runs, a browsed node re-fetches
in place (Back still goes where it did), and the root reloads every shelf.

## Tests

96 unit tests, all passing. New: `ProgressProjectionTest` — the spec's projection
formula, including the paused case, the ×1000 speed unit, clamping, a timestamp
slightly in the future, and the float `playback_speed` that used to take the whole
`server/state` down with it.

## Not verified on device

**None of this has been run against real hardware.** The diagnoses are grounded in the
code and in the Sendspin spec, and the arithmetic is unit-tested, but the symptoms were
reported from a device and have not been confirmed fixed on one. Worth checking:

1. A track starts at 00:00, with audio from the first moment.
2. The bar climbs smoothly through the first ten seconds — no run-ahead, no snap back.
3. Dragging the scrubber holds at the target, in-app and on the lock screen.
4. Skip sends the bar to 00:00, and it stays there until the new track runs.
5. Tapping the notification mid-playback resumes the app rather than restarting it.

`adb logcat -s SendspinAudio` still prints one `head released: err=…` per stream. A
`head late but earliest available` line means the clock was still converging and the
head was played unscheduled — correct content, momentarily out of step with a group.
