v0.3.3 — the audio skip fixed, enqueue matched to the reference client, and a way out of a stuck name
Debug build of Sendspin for Android (work in progress).

## Install
1. Download **sendspin-0.3.3-debug.apk** below onto your Android device (Android 12 / API 31+).
2. Allow **install from unknown sources** when prompted.
3. Open the APK. Installs over 0.3.x (versionCode 18).

## What's new since v0.3.2

### The audible skip a couple of seconds in — a 0.3.2 regression

0.3.2 started scheduling audio frames against the server clock, which was the right
idea and fixed tracks beginning part-way in. It scheduled **every** frame, and that
was wrong.

The clock filter needs a few round-trips to converge. So the first second or two of a
track played *unscheduled* (`isSynced()` still false) — running ahead of the server's
timeline — and then `isSynced()` flipped true mid-track and the decode loop suddenly
began blocking on frames whose moment the head start had already eaten. That stall is
what you heard as a skip on the second or third second.

Only the **head** of a stream is scheduled now, and after that the AudioTrack paces
playback itself at the stream's sample rate, exactly as it did before 0.3.2. The
decision is made once, at the point playback starts (and again after a seek or track
jump, which are the other places playback restarts from a known position), so it can
never flip mid-track. The start point stays correct; nothing after it can stall.

### Adding to the queue on the Music Assistant player

Found it. The app was omitting `radio_mode` from `player_queues/play_media`. It is a
defaulted parameter server-side, so leaving it out looked harmless — but Music
Assistant then falls back to the queue's own radio setting, and on a queue that
already had items the added tracks were dropped in favour of its generated ones. That
is precisely the reported behaviour: adding only worked when the queue was empty.

The call is now argument-for-argument what the official app sends
(`media`, `option`, `radio_mode`, `queue_id`, in that order).

The "Added N tracks" count is also honest again. 0.3.2 tried to verify the enqueue by
counting the queue before and after — but Music Assistant tops the queue up on its own
(radio mode, "don't stop the music"), so the difference counted tracks nobody added
and reported six or seven for a single track. That check is gone.

### The player name

The official Music Assistant app has **no rename call anywhere** — the name in
`client/hello` is the only mechanism, and it works there because its users choose a
name before the player first registers. Music Assistant keys a Sendspin player on its
`client_id` and keeps the name it was **first registered under**; the protocol has no
rename message.

So a player that first appeared as "Google Pixel 10" keeps that name, and the only
ways out are to edit its server-side config (which this app tries, and which needs
admin rights) or to arrive as a new player.

There is now a **Register again as a new player** button under the player name. It
mints a fresh client id and reconnects, so Music Assistant registers a new player
under the name you typed. The old entry stays in Music Assistant, greyed out, for you
to delete. It is blunt, but unlike everything tried so far it cannot fail.

## Known limits

The audio change is the one to listen to first. Its start-scheduling is skipped
entirely when the clock hasn't synced yet, so the very first track after connecting
may still begin slightly early — subsequent tracks won't.
