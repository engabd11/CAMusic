v0.3.2 — audio scheduled against the server clock, and the 0.3.1 fixes that didn't hold
Debug build of Sendspin for Android (work in progress).

## Install
1. Download **sendspin-0.3.2-debug.apk** below onto your Android device (Android 12 / API 31+).
2. Allow **install from unknown sources** when prompted.
3. Open the APK. Installs over 0.3.x (versionCode 17).

## What's new since v0.3.1

Device testing showed several 0.3.1 fixes weren't holding. Most had the same shape:
the app asked the server for something, the server declined or ignored it, and the
app reported success anyway. Where that was the case the request is now verified and
a refusal is shown rather than swallowed.

### Tracks started part-way in

The real one. `SendspinAudioEngine` parsed each frame's timestamp and then **threw it
away**, writing every frame to the audio track the moment it arrived. The Sendspin
spec is explicit that this is wrong:

> Binary audio messages contain timestamps in the server's time domain indicating when
> the audio should be played… Clients must translate this server timestamp to their
> local clock using the offset computed from clock synchronization.

Because the server streams as far ahead as `buffer_capacity` allows — several seconds
— the whole prefetched buffer was poured straight out on `stream/start`. That is why a
track sometimes began a few seconds in.

Frames are now scheduled: the timestamp is mapped onto the local clock through
`ClockSync` (a working, unit-tested Kalman filter that until now had **no reader at
all**), the player's `static_delay_ms` is subtracted, and frames that arrive already
late are dropped rather than played, as the spec requires. This should also be what
finally lets this phone stay in step with another speaker in a group.

### Adding to the queue on the Music Assistant player

`player_queues/play_media` returns nothing at all, so a queue that refused the items
was indistinguishable from one that took them — and the app said "Added to queue"
either way. Enqueue now counts the queue before and after and tells you plainly when
nothing landed. If it still fails, the message is the thing to report: it means the
server is declining the command, and the reason is now visible instead of silent.

### The player's name

0.3.1 wrote the name with `config/players/save`, which is right — but through a
**second, separately-authenticated connection**, and `config/players/save` is an
ADMIN command. On a server where that connection wasn't an admin the save was refused
and the error was swallowed by a bare `runCatching`, so the name simply stayed wrong.

It now goes over the app's own authenticated connection, waits for Music Assistant to
have actually registered the player, and **reads the config back to confirm**.
Whatever the server says is shown under the name field in Settings. Per the Sendspin
spec the protocol "provides no mechanism for updating the client name
post-connection", so this API call is the only route — if it is refused, that message
is the answer.

### Codec choice for the Music Assistant player

`preferred_sendspin_format` is a `ConfigEntry` whose allowed values the **server**
declares, and they carry the rate and depth (`flac_48000_16`), not a bare codec name.
0.3.1 sent `"flac"`, which isn't one of the declared options, so the save was rejected
and the whole thing was a no-op. The app now reads the options list off
`config/players/get` and picks the matching one — the same thing massdroid does.

The advertised `supported_formats` list was already being narrowed correctly; the spec
confirms the server takes "the first match it implements from the client's list".

### Navidrome quality

Two separate problems. The **badge** always read PCM because the Playing row was
hard-coded to the AudioTrack's own encoding, so changing the format looked like it did
nothing whatever the stream actually was. Playing now reports what is really being
decoded — the requested transcode, or the library file when streaming it untouched —
with the file's own format beside it as Source.

The quality control has also moved **into the Navidrome server card**, where it
belongs, instead of sitting in a section of its own.

### The timeline

An optimistic seek or skip now releases when this phone's Sendspin stream actually
starts, rather than when a poll happens to corroborate it — which is how the official
app does it, and is only possible now that the engine knows when audio really begins.
A remote speaker offers no such signal and still falls back to the poll.

## Still unverified

The queue, name and codec fixes turn silent failures into visible ones. If any of them
still doesn't work, the app will now say why, and that message is what's needed to
finish the job.
