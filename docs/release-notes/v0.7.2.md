v0.7.2 - the direct Hue path stops crashing, and starts sounding like the room is listening
Stable build of CAMusic for Android.

## Install
1. Download **camusic-0.7.2.apk** below (Android 12 / API 31+).
2. Allow **install from unknown sources**, then open it. Installs over 0.7.x (versionCode 31) — same signing key, so your servers, credentials and downloads survive.

Five changes on top of [v0.7.1](v0.7.1.md), all of them in the direct Hue Bridge path
that [v0.7.0](v0.7.0.md) introduced. Nothing else in the app is touched.

## Two crashes on the way into direct mode

Selecting the direct bridge closed the app; so did opening the Lights tab afterwards.

The certificate bundle was failing to load. The file is valid and in the APK, but it has
CRLF line endings, and Android's PEM reader stops at the first block it dislikes and
returns what it has — silently, with an empty collection and no exception. The loader now
finds the blocks itself and decodes the base64, which takes the text handling out of the
question. Real PKIX chain validation is unchanged.

That failure was fatal rather than reportable because the HTTP client was a constructor
default, so reading the bundle and building a TrustManagerFactory ran on the main thread
during composition — it took the app down while you were merely scrolling Settings. The
client is built on first request now, which puts the work on an IO dispatcher and turns a
TLS setup failure into a failed request.

The second was an initialisation-order race: an `init` block sat above the fields the
collectors it launched immediately read. Non-null types, so the compiler elides the check
and it surfaces as a null pointer on a field that cannot be null. The block now sits at
the end of the class, with a comment saying why it has to stay there.

## The show is livelier, because three of syncoV2's controls were inert

Reported as the same intensity rungs feeling flatter here than through Home Assistant.
Measured rather than guessed: of syncoV2's 61 mode parameters, seven were still declared
and never read. Three mattered.

**spectralPop** was the big one. Every rung sets it, but it was only read inside the
Extreme renderer — so Subtle through Intense had a beat flash over a smooth glow and
nothing in between. Each lamp now pops on a fresh transient anywhere in its own slice of
the spectrum: a kick lights the low lamps, a snare the low-mids, a guitar the mids, a
cymbal the highs. It is measured against a slow per-bin baseline, so a held note settles
and stops popping while a repeated hit keeps firing.

**fluxGate** is the phantom-beat killer — a beat arriving with no spectral movement
behind it is scaled away, so a drifted grid cannot keep flashing an empty bar. Only
Intense enables it, which is what lets Intense afford so permissive a beat gate.

**nobeatFlash**, and the rhythm-confidence tracker behind it, is what stops Intense
strobing through an ambient passage.

The continuous layer also starts from the rung's `base` brightness rather than its
`floor`, which is what syncoV2 does. They coincide on Subtle, so every other rung had
been running slightly dimmer than intended.

## Hits land on the side of the room they came from

The tap was folding to mono before the analyzer ever saw two channels, so the stereo
field was inert on every rung — a guitar hard left and a guitar hard right lit the room
identically. The ring now carries interleaved stereo, and both the melbank glow and the
attack pop are pan-weighted.

Pan is per frequency band, smoothed over about 100 ms, and is left *empty* on a silent
frame rather than reported as centred, because the engine needs to tell "no idea" from
"dead centre". Mono material is untouched: a centred mix comes out exactly as the
unweighted mean, and the test asserts that every feature except pan is bit-identical to
what the old mono path produced.

## Album colours are extracted for a room, not for a screen

Reported as the colours being wrong in a way they are not under Home Assistant. They
were. Light Sync had been reusing the app's own UI extraction, and the two answer
different questions.

The UI one picks an accent that must stay legible on black, so it ranks candidates by
vividness against size — a small bright splash deliberately beats a large flat field —
and then lifts lightness and saturation. Both are right for a swatch and wrong for a
room: they surface colours the sleeve barely contains, and a bulb has its own brightness
channel, so pre-lifting only distorts the hue.

The direct path now ranks purely by how much of the cover each colour occupies, because
the weights are dwell time. Near-duplicate hues pool their share. Near-neutral clusters
render as tinted whites — a bulb cannot show silver, but a dim cool white reads as it —
rather than being pushed into a hue they do not have, which is the classic "every
greyscale sleeve comes out gold" failure. Clustering is deterministic, so the same sleeve
lights the room the same way every time it plays. The UI keeps its own extraction, which
remains right for what it does.

## Vocal lamps shimmer

Vocal-role lamps now sparkle with the singing on top of their ordinary reaction, offset
per lamp so neighbours shimmer out of step and the room glitters rather than pulsing in
unison — and deterministically, so a lamp behaves the same way every time instead of
looking like noise. The sparkle replaces part of the lamp's steady level rather than
piling on top of it, so a vocal lamp reads as moving rather than simply brighter.

That closes the last reachable gap in the port. Two of syncoV2's 61 mode parameters
remain unread and both are genuinely unreachable: one belongs to the Movies effect that
was deliberately dropped, and one needs a per-track loudness profile only an offline scan
produces — syncoV2 itself falls back to uniform weighting without it, which is exactly
what a live tap gets.
