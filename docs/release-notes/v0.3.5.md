Debug build of Sendspin for Android (work in progress).

## Install
1. Download **sendspin-0.3.5-debug.apk** below (Android 12 / API 31+).
2. Allow **install from unknown sources**, then open it. Installs over 0.3.x (versionCode 20).

## What's new since v0.3.4

### Adding to the queue on the Music Assistant player — found, from the docs

The expanded Commands Reference has the answer, and it is a mistake that runs through
the whole app: **`player_queues/*` commands address a queue, not a player.** Every
queue command here was being handed a *player id* on the assumption that the two are
the same. For a player synced to another they are not — a synced player plays the
leader's queue.

So the tracks really were being added. To a queue nobody was listening to. And they
only became audible when playing that queue made it the active one — which is exactly
the reported symptom, that "add" appeared to work only when the list was empty.

Music Assistant answers the question itself with `player_queues/get_active_queue`
("Return the current active/synced queue for a player"), which the app now calls
instead of guessing. Play, shuffle, play-next and add on the album, artist, playlist
and library screens all go through it.

The stale claim that "a player's queue id equals its player id" is gone from the
repository's own documentation, so the next change doesn't inherit it.

### The registration check asks the right question

`syncPlayerConfig` looked for the phone by scanning `players/all`, whose documented
parameters include `return_unavailable`, `return_disabled` and
`return_protocol_players` — all defaulting off. A player that is any of those things
is simply absent from the list. It now asks `players/get` for that one player
directly, which has no such filters.

## Audit of every Music Assistant call

Checked against the expanded reference, command by command. Correct as sent:
`music/artists/artist_albums`, `artist_tracks`, `artists/get`, `albums/album_tracks`,
`albums/get`, `playlists/playlist_tracks`, `tracks/get`, `tracks/preview`,
`tracks/similar_tracks`, `search`, `favorites/add_item`, `favorites/remove_item`,
`recently_played_items`, `recently_added_tracks`, `in_progress_items`,
`recommendations`, `sonic_similarity/text_search`, `players/all`, `players/cmd/*`
(play, pause, stop, next, previous, seek, power, volume_set, group_volume,
set_members, ungroup, ungroup_many), `player_queues/all`, `items`, `clear`,
`delete_item`, `move_item`, `play_index`, `repeat`, `shuffle`,
`dont_stop_the_music`, `set_playback_speed`, `save_as_playlist`, `transfer`,
`config/players/get`, `config/players/save`.

`player_queues/play_media` matches the documented signature (`queue_id`, `media`,
`option`, `radio_mode`) — the only thing wrong with it was which id it was given.

Two things noted but deliberately not changed: the `library_items` commands document a
`kwargs` parameter the app omits (it is an artefact of the Python signature and the
calls work), and `player_queues/seek` exists alongside the `players/cmd/seek` the app
uses — worth revisiting if seek behaviour needs more work.

## Still open

**A queue that repeats its last track.** Not diagnosed. Repeating one track is what
`repeat_mode: "one"` does, and nothing in the app sets it except the repeat button, so
the next step is knowing what the Now Playing options sheet shows for **repeat mode**
and **Don't stop the music** at the moment it happens.
