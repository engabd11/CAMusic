## What's new since v0.3.5

Eight reported bugs. Reading the Music Assistant OpenAPI schema and the Subsonic spec
against the code, six of them turned out to be the app not using fields the servers
were already sending.

### The codec badge always agreed with the source

Because it was reading the source. `streamdetails.audio_format` is the format Music
Assistant *opened* — the file as the provider hands it over — and the app labelled
that "Playing". The format a given speaker actually receives lives somewhere else
entirely: `streamdetails.dsp` is a map of player_id → `DSPDetails`, and its
`output_format` is what goes down the wire.

`MaQueue` now carries both: `inputFormat` for the source and an `outputFormats` map
resolved per player, so a synced member reports what *it* is decoding rather than the
leader's format. "Transcoded from X to Y" means something for the first time.

Three fields that were being parsed and thrown away are now used or read properly:
`bit_rate` (normalised, so a provider reporting bits per second no longer renders as
"1411000k"), `channels`, and `streamdetails.provider` — which replaces the source
badge that said "MA" no matter which backend held the file.

### The queue panel didn't move when you added to it

Music Assistant events were being matched by looking for the substring "player" or
"queue" anywhere in the frame's JSON. Every event hit the same branch, so
`queue_items_updated` — the one event that means *the contents changed* — was
indistinguishable from the `queue_time_updated` MA emits about once a second, and the
single handler they shared only ever re-read `player_queues/all`.

Events are parsed by name now, with a dedicated collector for contents changes and an
item-count watcher behind it. That covers adds issued from the library and the album,
artist and playlist screens without those screens needing to know the queue panel
exists.

`player_queues/items` also sends `limit` and `offset` at last. It defaults to 500, so
anything longer was being silently truncated.

### The black box over the speaker picker

Sheets reserved room at the bottom for the tab bar *and* the mini player — 98dp in the
tab layout, 186dp in the overlay one — which is close enough to a third of the sheet.
And because a sheet is drawn inside its own screen, which is a `NavHost` sibling below
the tab bar, the bar's opaque black rect was painted over the top of it.

Sheets now reserve only the system navigation inset, and the bottom chrome stands down
while one is open. Fixes the speaker picker, the queue panel, the player options sheet
and the long-press sheet, in both layouts.

### Tracks starting a couple of seconds in

The head of a stream was scheduled against `ClockSync.isSynced()`, which is true after
a **single** clock round-trip — long before the Kalman filter has converged. An offset
still seconds wide meant the first frame was either held in silence while the server
ran on, or dropped as "late".

`isReadyForPlaybackStart()` — eight converged samples with bounded error — already
existed in the filter and was referenced nowhere. The gate uses it now, and stays armed
until a frame is actually released: clearing it *before* the check meant one dropped
head frame disabled scheduling for the rest of the stream and poured the server's
multi-second read-ahead straight into the track. Bounded at four seconds, after which
it plays unscheduled rather than sitting silent.

The decision is split into a pure `HeadGate` so it can be tested off-device, and the
engine logs one `head released: err=… stall=…` line per stream — `adb logcat -s
SendspinAudio` will say directly whether the clock converged.

On the Navidrome side, `estimateContentLength=true` is now sent for transcoded streams.
Without it the response is chunked with no `Content-Length`, and MediaPlayer's own byte
`Range` probes get resolved by the server into a *time* offset — the same symptom from
a completely different direction.

### Long-press anything in the library

Play now, play next, add to queue, download. The old track sheet is generalised to any
media type: Music Assistant takes an artist, album or playlist uri on `play_media`
exactly as it takes a track's, so all three actions mean the same thing whatever you
pressed. Works on the library grid and rows, on search results, and on the album rows
of the artist screen.

### Favourite albums and artists

The repository layer already handled every media type — `music/favorites/add_item`
takes any item's uri, and Subsonic's `star` has `albumId` and `artistId` parameters.
The heart was gated to Music Assistant *tracks* for no reason either server imposed.

Now on albums, artists and playlists too, with toggles on the album and artist heroes.
Also fixes a real bug on the album screen, where the heart only rendered for tracks
that were *already* favourites — so the handler was reachable to un-favourite and
nothing else, and a track could never be favourited from there.

### Favourites lead the library

Favourite albums → Favourite artists → Continue listening → Recently added → For you →
Recently played, using `music/albums|artists/library_items` with `favorite=true`, which
the API has always accepted. "Recently played" also seeds its hearts now; it was the
one shelf loader that never did.

### "Ready — announcements will play here", while a speaker played an album

Nothing outside the UI knew what the selected player was doing, because the only thing
that tracked it was a ViewModel — and a ViewModel dies with the Activity. So the shade
fell back to the connection notification, which only ever knew about this phone's own
Sendspin stream.

A new process-scoped `MaNowPlaying` follows the selected player. The media notification
shows its artwork, track and position, and names the speaker. The connection
notification stops claiming the phone is idle when it isn't.

That fixed a second bug on the way: the media session's transport callbacks addressed
`Playback.playerId` — this phone — regardless of which speaker was selected. A headset
button pressed while a speaker was playing paused the phone, which was not the thing
making any sound.

## Subsonic conformance, fixed in passing

- **`scrobble` was inverted.** `submission=true` means a *completed* play; the app sent
  it the instant a track started, so every one-second skip counted as a full play and
  Navidrome's counts drifted upwards. It now sends `submission=false` at start and
  `submission=true` with `time` after half the track or four minutes, whichever comes
  first — and only if the track is still the one playing.
- **`getAlbumList2` was asked for `size=5000`** against a documented maximum of 500.
  Paged now, publishing batches as they land.
- **`bitDepth` no longer guesses 16** when the server doesn't report it, which made
  every track on a plain Subsonic server claim CD depth it had never mentioned.
- `44100 / 1000` rendered as "44kHz" in the Settings format readout.

## Tests

85 unit tests, all passing. New: `MaStreamDetailsTest` (the dsp map and its fallback
chain, bitrate normalisation, queue-item page offsets), `MaEventTest` (event
classification), `HeadGateTest` (the head-of-stream decision).
`ClockKalmanFilterTest` now locks in the readiness contract the audio engine depends
on — one round-trip is "synced" but not enough to schedule against.

## Not verified on device

The sheet layout, the stream start offset and the new notification all need a real
device against a live server. For the start offset in particular, the diagnosis is
solid in code but the fix wants confirming: `adb logcat -s SendspinAudio` should show
one `head released:` per track and never `clock never converged`.
