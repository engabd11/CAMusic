v0.4.1 — v0.4.0 did not open
Debug build of Sendspin for Android (work in progress).

## Install
1. Download **sendspin-0.4.1-debug.apk** below (Android 12 / API 31+).
2. Allow **install from unknown sources**, then open it. Installs over 0.3.x / 0.4.0 (versionCode 24).

**v0.4.0 crashed on launch and has been withdrawn.** If you installed it, this
replaces it. Everything in the [v0.4.0 notes](v0.4.0.md) is in this build — the audit
against the Music Assistant, Sendspin and Subsonic specifications, the gapless work,
the ExoPlayer move and applied ReplayGain. This release adds nothing but the two
fixes below.

## What went wrong

Two properties were read before they had been initialised. Both bugs predate the
0.4.0 work and were exposed by it rather than caused by it — which is also why the
unit tests, lint and the build all stayed green: nothing off-device runs a
`ViewModel` constructor.

`viewModelScope` is `Dispatchers.Main.immediate`. On the main thread it does **not**
defer: `stateIn(..., Eagerly)` runs its combine right there, and `collect` on a
`StateFlow` runs its lambda with the current value right there. Kotlin initialises
properties in source order. So anything either of those touches has to be declared
*above* it — otherwise it is still null when it is read.

- **The app died on open.** `NowPlayingViewModel._radioMode` was declared next to
  `toggleRadioMode()` near the bottom of the file, where it reads naturally. But
  `maState` uses it, and `maState` is an eager `stateIn` some six hundred lines
  earlier. It was null every time, so every launch was an NPE before the first frame.

- **And again when the library loaded.** `LibraryViewModel._frequent` was declared
  beside `loadFrequent()`. `init` collects the API connection state; a server that is
  already connected emits immediately; that calls `showRoot()`, which fans out into
  every shelf loader including that one.

Both now sit with the other backing flows, carrying a comment explaining why they
live somewhere less natural than they read. `NowPlayingViewModel` already had exactly
that note on another property — *"declared before init deliberately — property
initialisers run in source order"* — and these two were added later, by a different
change, without it.

`LocalPlayer.playerListener` moved above the function that installs it for the same
reason. Nothing builds the player during construction today, so that one was only
ever latent, but it is one refactor from the same crash.

The rest of the codebase was swept for the pattern: `Playback` runs on
`Dispatchers.Default`, which always dispatches, and `ArtistDetailViewModel`'s
late-declared flow is not reachable from its `init`.

## Verified on device

This build was installed on a Galaxy S23 (Android 15) and driven before release —
which is the step that was missing last time:

- Launches to the library, with covers and shelves populated from a live Music
  Assistant server.
- All four tabs — Library, Speakers, Lights, Settings — no crash.
- Into Albums, into an album, into Now Playing — no crash.
- Zero FATAL entries in the crash buffer across the whole run.
- Quality badge reads **FLAC · 48/24** against the live server, so the 24-bit path
  negotiates and renders.

## Still not verified

The **audio behaviour** from v0.4.0 still needs ears, and a launch test does not
provide them. Unchanged from those notes:

1. A continuous album over Music Assistant — no gap and no clipped tail between tracks.
2. Repeated seeking never plays a burst of the old position.
3. In a group: the phone stays silent until its clock converges, and the sync delay
   audibly shifts it. **Check the sign of that control against a second speaker** —
   the specification's sense is the opposite of Music Assistant's own.
4. Headphones unplugged pauses on both backends.
5. On Navidrome: gapless album, ReplayGain audibly different between off and album,
   USB DAC still routed.
